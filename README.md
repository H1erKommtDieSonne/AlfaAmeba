# Запуск AlfaAmeba и DocumentNode Portable

Инструкция по комплекту от 26.10.2026: `AlfaAmeba-backend-current.tar.gz`,
`DocumentNode-Portable-previous.zip`, `Successful-Mock-Applications.zip`.
Параметры сверены с исходниками этих архивов. Если используется более новая версия,
сначала сравните её `compose.yaml`, `.env.example` и API-контракты.

DocumentNode — Python/FastAPI-сервис обработки документов, а не Node.js.
Для полного запуска через Docker отдельно устанавливать Python и Node.js не нужно.
Код Django находится в `AlfaAmeba/`, код ноды — в `DocumentNode-Portable/`.
Все команды `docker compose` ниже выполняются из соответствующей папки.
Примеры адресов и секретов нужно заменить своими значениями.

## Архитектура и контейнеры

```text
Браузер → nginx :8080 → Django → PostgreSQL
                          │
                          ├─ внутренние pull-очереди → локальные воркеры
                          │
                          └─ NodeJob → node-sender → DocumentNode API :8000
                                                       │
                                                  Redis / RQ
                                                       │
                                                     worker
                                                       ├─ Ollama: извлечение / Vision
                                                       ├─ финансовые расчёты
                                                       ├─ ml_node: годовые прогнозы
                                                       └─ Ollama: итоговая сводка
                                                            │
Django ← callback и feedback ← callback_worker ← сохранённый результат
```

Основной путь интеграции — отправка документов в `/jobs` и обратный callback.
Django не вызывает Ollama напрямую и не обязан напрямую вызывать ML API.

### Compose Django

| Сервис | Назначение | Доступ |
| --- | --- | --- |
| `nginx` | Вход в кабинет, проксирование Django, статика | Порт хоста `APP_PORT`, обычно 8080 |
| `django` | Пользователи и роли, продукты, заявки и версии, документы, результаты и аудит; Gunicorn | Внутри сети `django:8000` |
| `postgres` | Основная БД PostgreSQL 17 | Внутри сети `postgres:5432` |
| `ml` | Локальный разбор текстовых документов и health API; запускает pull-worker потоком | Внутри сети `ml:9000` |
| `ml-worker-documents` | Отдельный демонстрационный documents-worker (`--stage documents`) | HTTP-порта нет |
| `ml-worker-analytics` | Демонстрационная аналитика (`--stage analytics`) | HTTP-порта нет |
| `node-sender` | Отправка `NodeJob` во внешнюю ноду; общие с Django БД и media | Только профиль `node-sender` |

В архивной сборке `ml` действительно разбирает файлы через `ml.extraction` и
`ml.analysis`, без LLM/OCR. Вызов `ml.worker --stage ...` переключает на
`ml.stub_worker`. Поэтому `ml` и demo documents-worker могут конкурировать за
одну внутреннюю очередь. Их результаты не следует смешивать с результатом
внешнего `NodeJob`: это разные контуры. Для проверки реальной документной ноды
смотрите именно результат DocumentNode в карточке заявки.

### Compose DocumentNode

| Сервис | Назначение | Доступ |
| --- | --- | --- |
| `api` | FastAPI: приём файлов, постановка задач, результат и схемы | Хост `127.0.0.1:8000` по умолчанию |
| `worker` | RQ-очередь `docs`: извлечение, расчёты, ML, итоговая LLM-сводка | HTTP-порта нет |
| `callback_worker` | Очередь `callbacks`, доставка результата и замечаний в Django | HTTP-порта нет |
| `cleanup` | Периодическая очистка исходников и результатов | HTTP-порта нет |
| `redis` | Очереди RQ и служебные состояния | Только сеть Compose, порт 6379 |
| `ollama` | Локальный сервер LLM | Только сеть Compose, `ollama:11434` |
| `mock_bo` | Синтетический поставщик годовой отчётности | Профиль `mock`, хост 8010 |
| `ml_node` | Пять обученных годовых ML-моделей | Профиль `ml`, хост 8020 |

Запускатели включают оба профиля `mock` и `ml`. У двух проектов собственные
Docker-сети; имя `api` из сети Django автоматически не разрешается.

## Первый запуск Django

Нужны Docker Engine с Compose v2 либо Docker Desktop с Linux containers/WSL2.
Проверьте `docker version` и `docker compose version`. Интернет нужен для
образов, Python-зависимостей и standalone Tailwind, который Dockerfile скачивает
и использует при сборке CSS.

Распакуйте архивы в отдельные соседние папки, например:

```text
deployment/
  AlfaAmeba/
  DocumentNode-Portable/
  Successful-Mock-Applications/
```

В `AlfaAmeba/` создайте `.env`, если его ещё нет:

```powershell
Copy-Item .env.example .env
```

На Linux вместо `Copy-Item` используйте `cp`. Не перезаписывайте существующий
настроенный `.env`. Заполните как минимум:

```dotenv
POSTGRES_DB=credit
POSTGRES_USER=credit
POSTGRES_PASSWORD=<случайный-hex-пароль>
DJANGO_SECRET_KEY=<отдельный-длинный-секрет>
DJANGO_ALLOWED_HOSTS=localhost,127.0.0.1,django
DJANGO_CSRF_TRUSTED_ORIGINS=http://localhost:8080,http://127.0.0.1:8080
DJANGO_SECURE_COOKIES=false
APP_PORT=8080
LLM_SERVICE_TOKEN=<отдельный-токен-внутренней-очереди>
ANALYTICS_SERVICE_TOKEN=<другой-токен-внутренней-аналитики>
DOCUMENT_NODE_ENABLED=false
```

Каждое значение в `<...>` заменяется целиком. Для генерации одного секрета:

```powershell
python -c "import secrets; print(secrets.token_hex(32))"
```

Если Python на хосте отсутствует:

```powershell
docker run --rm python:3.12-slim python -c "import secrets; print(secrets.token_hex(32))"
```

Повторите генерацию для каждого независимого секрета. Hex удобен для пароля БД:
Compose собирает `DATABASE_URL`, поэтому символы `@ : / ? #` требуют специального
кодирования и в этом примере не используются. Хост `django` в allowed hosts нужен
внутренним воркерам. Для входа по IP/домену добавьте этот IP/домен в allowed hosts,
а полный origin с протоколом и портом — в trusted origins.

```powershell
docker compose config --quiet
docker compose up -d --build --wait
docker compose ps
```

Команда сервиса `django` сама выполняет `migrate`, `collectstatic`, затем запускает
Gunicorn. Откройте [кабинет](http://localhost:8080/login/).
В Docker используются `config.settings.prod` и PostgreSQL, а не SQLite с хоста.
Для HTTPS настройте TLS на входном прокси и `DJANGO_SECURE_COOKIES=true`;
имеющийся nginx-конфиг сам сертификаты не выпускает.

## Тестовые пользователи

На новом демонстрационном стенде:

```powershell
docker compose exec django python manage.py seed_demo
```

| Email | Роль | Пароль |
| --- | --- | --- |
| `business@example.test` | Представитель бизнеса | `DemoPass123!` |
| `bank@example.test` | Кредитный специалист | `DemoPass123!` |
| `senior@example.test` | Старший согласующий | `DemoPass123!` |
| `admin@example.test` | Администратор банка | `DemoPass123!` |

`seed_demo` создаёт/обновляет каталог продуктов, организацию и две синтетические
заявки с уже сохранёнными demo-результатами. Это проверка интерфейса, а не
подтверждение обращения к работающей LLM. Повторный запуск **сбрасывает пароли**
этих четырёх пользователей и обновляет demo-результаты; используйте на тестовой БД.

Для Django admin создайте отдельного суперпользователя:

```powershell
docker compose exec django python manage.py createsuperuser
```

Логин — email. Откройте [Django admin](http://localhost:8080/admin/).
`admin@example.test` имеет банковскую роль, но `seed_demo` не делает его
суперпользователем Django. Обычная регистрация создаёт роль `BUSINESS`.
Сотрудник обрабатывает заявку, старший согласующий принимает итоговое решение;
банковские роли не подают клиентские заявки. Демо-пароли предназначены только
для изолированного тестового стенда.

## Первый запуск DocumentNode

В папке `DocumentNode-Portable/`:

```powershell
# Windows, NVIDIA GPU — стандартный режим:
.\start.ps1
# Либо CPU:
.\start.ps1 -Cpu
```

На Linux:

```bash
bash start.sh
# Либо CPU:
bash start.sh --cpu
```

Для GPU нужны NVIDIA-драйвер и поддержка контейнерного GPU; на Linux — NVIDIA
Container Toolkit, на Windows — GPU в WSL2. CPU-режим значительно медленнее.

Скрипт копирует `.env.example`, генерирует отдельные `API_KEY` и `ML_API_KEY`,
собирает образы, включает профили `mock`/`ml`, поднимает Redis/Ollama, скачивает
`qwen3.5:35b-a3b` при отсутствии и запускает остальные сервисы.
Веса LLM в архиве отсутствуют. По README комплекта модель занимает примерно
22 ГБ; заложите не менее 40 ГБ свободного диска и запас RAM/VRAM. Это ориентир
авторов комплекта, а не гарантированный минимум для любого оборудования.
Скрипт сохраняет существующие ключи и Docker-volumes.

Поддерживаемые флаги этой версии: `-Cpu`, `-SkipModelPull` на Windows;
`--cpu`, `--skip-model-pull` на Linux. Пропуск скачивания всё равно проверяет
наличие модели. Упомянутые в старом `ml_node/README.md` флаги `-MlOnly`, `-NoMl`
и `compose.ml.yaml` в этом архиве отсутствуют — не используйте их.

Проверки с хоста:

```powershell
curl.exe http://127.0.0.1:8000/health
curl.exe http://127.0.0.1:8010/health
curl.exe http://127.0.0.1:8020/ready
```

Swagger: [Document API](http://127.0.0.1:8000/docs),
[ML API](http://127.0.0.1:8020/docs),
[mock API](http://127.0.0.1:8010/docs). На Linux команда называется `curl`.
Ключи возьмите из локального `.env`; не публикуйте файл.

## Соединение Django и ноды

### Ключи и переменные

| Django `.env` | DocumentNode `.env` | Смысл |
| --- | --- | --- |
| `DOCUMENT_NODE_API_KEY` | `API_KEY` | Одинаковый ключ Django → API ноды, `X-API-Key` |
| `DOCUMENT_NODE_CALLBACK_TOKEN` | `CALLBACK_TOKEN` | Другой общий секрет нода → Django, Bearer |
| `DOCUMENT_NODE_URL` | — | База URL ноды, без `/jobs` |
| — | `CALLBACK_URL` | Полный URL `/api/v1/document-node/callback/` Django |
| — | `FEEDBACK_URL` | Полный URL `/api/v1/document-node/feedback/` Django |
| `DOCUMENT_NODE_PROVIDER_URL` | — | База mock-провайдера, без пути `/metrics` |
| — | `ML_API_KEY` | Отдельный ключ сервиса годовых моделей |

`LLM_SERVICE_TOKEN` Django относится к внутреннему pull-API; к авторизации Ollama
или DocumentNode он не относится. `API_KEY`, callback-секрет и ML-ключ различаются.

### Оба проекта на одном Windows/Docker Desktop сервере

Сохраните порты Django 8080 и ноды 8000. В `DocumentNode-Portable/.env`:

```dotenv
NODE_BIND_IP=0.0.0.0
CALLBACK_URL=http://host.docker.internal:8080/api/v1/document-node/callback/
FEEDBACK_URL=http://host.docker.internal:8080/api/v1/document-node/feedback/
CALLBACK_TOKEN=<общий-callback-секрет>
```

В `AlfaAmeba/.env`:

```dotenv
DOCUMENT_NODE_ENABLED=true
DOCUMENT_NODE_URL=http://host.docker.internal:8000
DOCUMENT_NODE_API_KEY=<API_KEY-из-ноды>
DOCUMENT_NODE_CALLBACK_TOKEN=<общий-callback-секрет>
DOCUMENT_NODE_PROVIDER_URL=http://host.docker.internal:8010
DOCUMENT_NODE_PROVIDER_API_KEY=
DJANGO_ALLOWED_HOSTS=localhost,127.0.0.1,django,host.docker.internal
```

`0.0.0.0` публикует порты ноды на интерфейсах хоста: ограничьте доступ сетью
стенда/firewall. Можно указать конкретный доступный IP хоста вместо wildcard.
Настройку loopback по умолчанию нельзя просто оставить при доступе через
`host.docker.internal`. Если Django работает процессом на хосте, а не контейнером,
он может обращаться к ноде по `http://127.0.0.1:8000`; Django тогда запустите
на 8080, чтобы не занять порт ноды.

### Оба проекта на одном Linux сервере

Можно использовать доступный из Docker частный IP хоста для обоих направлений.
Другой вариант — те же адреса `host.docker.internal`, что выше, и файл
`compose.host.yaml` **в каждом проекте**:

```yaml
# В AlfaAmeba/compose.host.yaml
services:
  django:
    extra_hosts: ["host.docker.internal:host-gateway"]
  node-sender:
    extra_hosts: ["host.docker.internal:host-gateway"]
```

```yaml
# В DocumentNode-Portable/compose.host.yaml
services:
  callback_worker:
    extra_hosts: ["host.docker.internal:host-gateway"]
```

Подключайте файл через `-f compose.yaml -f compose.host.yaml` ко всем последующим
командам соответствующего проекта. Для GPU добавляйте также `-f compose.gpu.yaml`.
Готовый `start.sh` не подключает `compose.host.yaml`: после первичной установки
пересоздайте сервисы командой с нужными `-f`. В этой схеме также нужен
`NODE_BIND_IP=0.0.0.0` либо доступный IP хоста.

### Django и DocumentNode на разных серверах

Пример: Django `192.168.1.103`, нода `192.168.1.105`.

В Django:

```dotenv
DOCUMENT_NODE_ENABLED=true
DOCUMENT_NODE_URL=http://192.168.1.105:8000
DOCUMENT_NODE_API_KEY=<API_KEY-из-ноды>
DOCUMENT_NODE_CALLBACK_TOKEN=<общий-callback-секрет>
DOCUMENT_NODE_PROVIDER_URL=http://192.168.1.105:8010
DJANGO_ALLOWED_HOSTS=localhost,127.0.0.1,django,192.168.1.103
DJANGO_CSRF_TRUSTED_ORIGINS=http://192.168.1.103:8080,http://localhost:8080,http://127.0.0.1:8080
```

В ноде:

```dotenv
NODE_BIND_IP=192.168.1.105
CALLBACK_URL=http://192.168.1.103:8080/api/v1/document-node/callback/
FEEDBACK_URL=http://192.168.1.103:8080/api/v1/document-node/feedback/
CALLBACK_TOKEN=<общий-callback-секрет>
```

Нужна двусторонняя связность: Django/sender → нода:8000 и provider:8010,
callback_worker → Django:8080. Для основной цепочки порт ML 8020 между серверами
не требуется: нода обращается к `ml_node:8000` в своей сети. Redis, PostgreSQL
и Ollama не нужно публиковать. Для соединений через недоверенную сеть используйте
TLS/VPN и адреса HTTPS на прокси. `localhost` внутри контейнера означает сам
контейнер; Docker-имена другого Compose-проекта без общей сети не работают.

### Применение настроек и включение sender

В папке ноды, CPU:

```powershell
docker compose --profile mock --profile ml up -d --build
```

Для GPU вместо этого:

```powershell
docker compose -f compose.yaml -f compose.gpu.yaml --profile mock --profile ml up -d --build
```

В папке Django:

```powershell
docker compose --profile node-sender up -d --build --wait
docker compose logs -f node-sender
```

При Linux-варианте с host gateway добавьте описанный выше override. После изменения
`.env` используйте `up -d`, чтобы Compose пересоздал контейнеры; обычный `restart`
не подставляет новые переменные окружения.

Встроенный mock-провайдер не содержит все возможные ИНН. Пустой
`DOCUMENT_NODE_PROVIDER_URL` выключает получение внешней годовой отчётности;
остаётся извлечение из приложенных документов. Отсутствующие данные не заполняются
нулями. Изменение адреса/модели не пересчитывает завершённые заявки — создайте
новую попытку расчёта через карточку сотрудника.

## API и авторизация

### Django: кабинет и формы

Это серверные HTML-страницы и формы с сессиями Django, не универсальный REST CRUD.
Изменяющие формы требуют CSRF. UUID обозначены как `{id}`.

| Метод | Путь | Функция |
| --- | --- | --- |
| GET, POST | `/register/` | Регистрация представителя бизнеса |
| GET, POST | `/login/` | Вход по email и паролю |
| POST | `/logout/` | Завершение сессии |
| GET | `/dashboard/` | Переход в раздел своей роли |
| GET, POST | `/` | Кабинет бизнеса, создание заявки с документами |
| GET | `/financing-advice/` | Подбор финансирования по входным параметрам |
| GET | `/applications/` | Список собственных заявок |
| GET, POST | `/applications/{id}/` | Карточка и отправка доработанной версии |
| GET | `/applications/{id}/success/` | Подтверждение отправки |
| GET | `/bank/` | Банковская очередь по правам роли |
| GET, POST | `/bank/applications/{id}/` | Карточка, комментарии, действия и подтверждение данных для расчёта |
| GET | `/bank/admin-dashboard/` | Обзор пользователей для администратора банка |
| GET | `/organization/access/` | Устаревший маршрут, редирект в кабинет |
| GET | `/bank/access-requests/{int_id}/review/` | Устаревший маршрут, редирект для администратора |
| GET | `/documents/{document_id}/download/` | Скачивание с проверкой доступа к заявке |
| GET, POST | `/admin/` и дочерние пути | Админка Django, staff/superuser |

POST карточки банка различает `form_type=comment`, `form_type=node_inputs`
и форму действия. Действия: `take`, `request_revision`, `send_to_approval`,
`approve`, `decline`, `return_to_review`; допустимость зависит от роли и статуса.
Указание action само по себе прав не выдаёт.

### Django: внутренние pull-API

База документов: `http://django:8000/api/v1/llm`.
Заголовок `Authorization: Bearer <LLM_SERVICE_TOKEN>`.

| Метод | Путь относительно базы | Назначение / JSON |
| --- | --- | --- |
| POST | `/jobs/claim/` | `{"worker_id":"worker-1"}` → задача, snapshot, документы, lease; 204, если пусто |
| GET | `/jobs/{job_id}/documents/{document_id}/` | Файл; дополнительно `X-Lease-Token` |
| POST | `/jobs/{job_id}/renew/` | `{"lease_token":"..."}` → продление аренды |
| POST | `/jobs/{job_id}/complete/` | `lease_token`, `documents`, `summary` → сохранение результата |
| POST | `/jobs/{job_id}/fail/` | `lease_token`, `error`, `retryable` (boolean) → ошибка/повтор |

База аналитики: `http://django:8000/api/v1/analytics`.
Заголовок `Authorization: Bearer <ANALYTICS_SERVICE_TOKEN>`.

| Метод | Путь относительно базы | Назначение / JSON |
| --- | --- | --- |
| POST | `/jobs/claim/` | Непустой `worker_id` → входные данные, lease, `input_hash`; 204, если пусто |
| POST | `/jobs/{job_id}/complete/` | `lease_token`, `input_hash`, `result` → результат schema 1.0 |
| POST | `/jobs/{job_id}/fail/` | `lease_token`, `error`, `retryable` → ошибка/повтор |

Типовые ответы: 400 — некорректное тело, 401 — токен, 404 — задача/файл,
409 — конфликт состояния, аренды или результата, 503 — служебный токен не задан.
Контракты результатов смотрите в `documents/services.py`, `analytics/services.py`
и `ml/queue_client.py` Django-проекта. Через nginx обе pull-базы специально
возвращают 404; внешний DocumentNode ими не пользуется.

### Django: приём результата внешней ноды

Оба адреса доступны через nginx. Авторизация:
`Authorization: Bearer <DOCUMENT_NODE_CALLBACK_TOKEN>`, тело `application/json`.

| Метод | Путь | Контракт |
| --- | --- | --- |
| POST | `/api/v1/document-node/callback/` | Полный сохранённый ответ ноды с `job_id` и результатом; до 2 MiB |
| POST | `/api/v1/document-node/feedback/` | `feedback_id` (UUID), `job_id`, `issues` (1–50); до 256 KiB |

`issues` содержит обязательные `code`, `message`; необязательные `field`,
`document_id`, `filename`, `suggestion`. `document_id` должен относиться к версии
этой задачи. Заголовки `X-Job-ID` и `Idempotency-Key` callback_worker дополняют
тело, но не заменяют Bearer-токен.

200 — принято или идентичный повтор; 400 — неверный контракт; 401 — ключ;
404 — неизвестный внешний job_id (возможна гонка после приёма нодой);
409 — несовместимое состояние/другой результат; 413 — размер; 415 — Content-Type;
503 — callback-секрет в Django пуст. Получение feedback не меняет решение банка.

## Модели и инференс

**LLM:** по умолчанию `qwen3.5:35b-a3b`, запускаемая Ollama. Один тег используется
для извлечения структурированных фактов, распознавания сканов/изображений и
итоговой сводки. DOCX и текстовые PDF сначала читаются штатными парсерами;
поддержанный банковский CSV разбирается детерминированно. Лимиты текстового
извлечения: фрагменты по 12000 символов, максимум 12 фрагментов на комплект.
Контекст LLM — 32768 токенов, запросы без streaming, `temperature=0`,
структурированные JSON-ответы. Запрос может длиться до 1800 секунд,
RQ-задача — до 10800 секунд. Наличие API health не проверяет успешность инференса.

### Что делает LLM на каждом этапе

В комплекте используется **одна LLM `qwen3.5:35b-a3b` в трёх ролях**.
Это разные вызовы с разными входами, промптами и схемами ответа, а не три
отдельные обученные модели.

| Этап | Что получает | Что делает и возвращает | Для чего используется |
| --- | --- | --- | --- |
| Распознавание документов — Vision (`api/vision.py`) | Изображения страниц скана PDF, JPG/PNG или кадров TIFF | Переписывает текст страницы в `transcription`, отмечает нечитаемые места в `uncertain_fragments`; не должна додумывать цифры | Превращает скан в текст для следующего этапа извлечения |
| Извлечение фактов (`api/analysis_pipeline.py`, `api/finance_prompt.py`) | Текстовый фрагмент документа, имя файла, контекст заявки и требования сервера | Классифицирует документ, извлекает финансовые показатели и реквизиты, отмечает проблемы; возвращает `ExtractionResponse` по JSON Schema | Подготавливает проверяемые факты для финансовых расчётов и входов ML |
| Итоговый анализ (`api/final_analysis.py`) | Отобранный JSON `evidence`: продукт, цель, сумма и срок заявки, готовность данных, рассчитанные показатели, ML-выходы и предупреждения | Составляет русскоязычную сводку, объясняет риски, пробелы и противоречия, предлагает дальнейшие проверки | Помогает сотруднику прочитать результаты в контексте конкретной заявки |

**Vision** вызывается для изображений и PDF, где нельзя получить достаточно
текста обычным парсером. Это этап чтения, а не финансового прогнозирования:
его результат ещё нужно проверить и преобразовать в структурированные факты.

**Извлечение фактов** собирает, например, годовую выручку и прибыль, активы
и обязательства, месячные денежные потоки, явно указанные платежи по долгам,
номера счетов и договоров. Наблюдения сопровождаются единицами, периодом
и источником: файл, страница/строка/таблица, подтверждающая цитата. Модель
не должна подменять отсутствующие значения нулями, составлять вымышленный
график платежей или выдавать чистую прибыль за денежный поток. Контракт
и последующая серверная проверка ограничивают принимаемый результат;
сам ответ LLM не подтверждает достоверность документа.

**Итоговый анализ** получает агрегированные данные по белому списку, без
исходных файлов, имён файлов, ИНН и цитат. Он сопоставляет цель с продуктом,
запрошенную сумму с уже рассчитанным ML-лимитом, а платёж — с доступными
показателями денежного потока и долговой нагрузки. Если показателя нет,
он должен отметить пробел. Эта LLM не создаёт собственные прогнозы, PD,
рейтинг или решение банка и не заменяет результаты пяти ML-моделей.

**Годовые ML-модели:** включён артефакт
`ml_node/models/credit_risk_suite_full.joblib`, manifest — `ml_node/model-info.json`.
Пять выходов: чистая маржа, выручка, вероятность убытка, операционная маржа,
вероятность кризиса ликвидности. Модели работают на CPU; образ использует
закреплённые зависимости. Загрузчик проверяет SHA-256 и совместимость версии
scikit-learn из manifest. Эти веса — отдельный компонент, замена LLM их не меняет.

DocumentNode вызывает ML только при готовых годовых входах; результат находится
в `result.financial_analysis.model_outputs`, аудит — `model_audit`.
Статусы: `completed`, `not_run`, `failed`. Неизвестные значения остаются null.
CSV и месячные суммы — рубли, годовые ML-входы — тысячи рублей; вероятности
ML в ответе — проценты 0–100. Смешение единиц даёт неверные расчёты.

### Что делает каждая из пяти ML-моделей

Пять моделей используют общий препроцессор и один набор годовых финансовых
признаков. Три модели дают числовой прогноз через `predict`, две — вероятность
положительного класса через `predict_proba`. При переданном `reporting_year`
API маркирует прогноз годом `target_year = reporting_year + 1`.

| Ключ модели в bundle | Назначение | Поле результата в `model_outputs` | Использование |
| --- | --- | --- | --- |
| `revenue` | Прогноз годовой выручки компании. Сервис преобразует прогноз из логарифмической шкалы через `exp` | `forecast_revenue_rub_thousands`, тысячи рублей | Основа расчётного кредитного лимита по правилам сервиса |
| `net_margin` | Прогноз чистой рентабельности: какой процент выручки составляет чистая прибыль | `net_margin_percent`, проценты | Оценка прибыльности; значение ниже 1% уменьшает расчётный лимит вдвое, если не сработали правила отказа |
| `operating_margin` | Прогноз операционной рентабельности: отношение операционной прибыли к выручке | `operating_margin_percent`, проценты | Отдельный показатель результата основной деятельности; в текущей функции рекомендации отдельного порога для него нет |
| `prob_loss` | Оценка вероятности убытка по положительному классу обученного классификатора | `loss_probability_percent`, 0–100% | Значение строго выше 40% даёт рекомендацию `rejected` |
| `prob_liquidity_crisis` | Оценка вероятности кризиса ликвидности по положительному классу обученного классификатора | `liquidity_crisis_probability_percent`, 0–100% | Значение строго выше 50% даёт рекомендацию `rejected`, если ранее не сработал порог убытка |

Вероятность убытка и вероятность кризиса ликвидности — разные оценки: компания
может показывать прибыль, но испытывать недостаток денег для текущих платежей.
Обе вероятности не являются вероятностью дефолта по кредиту или вероятностью
одобрения. Точные правила разметки целевых событий и состав обучающей выборки
не описаны в приложенном manifest; API-код сам по себе их не устанавливает.

**Общие входы:** годовая выручка, чистая и операционная прибыль, активы,
собственный капитал, оборотные активы, краткосрочные обязательства, деньги,
дебиторская задолженность и группа ОКВЭД. Препроцессор выводит из них маржи,
оборачиваемость активов, показатели текущей и денежной ликвидности,
отношения дебиторки к выручке, обязательств и капитала к активам и другие
признаки. В текущей реализации `debt_to_assets` использует именно краткосрочные
обязательства, а не весь долг компании.

Дополнительные признаки — валовая маржа `gross_margin`, годовой рост выручки
`revenue_growth_1y`, число лет убытка `loss_streak`. Если их не передали,
используются допущения исходного препроцессора: медиана обучения для валовой
маржи и нули для роста и серии убытков. Неизвестная группа ОКВЭД кодируется
как `99`. Эти подстановки перечисляются в `feature_assumptions`; это
технические значения для инференса, а не подтверждённые факты о компании.

**Лимит и рекомендация — правила поверх прогнозов, а не шестая ML-модель.**
Код `ml_node/scoring.py::recommendation` сначала считает лимит:

```text
базовый лимит = 0.20 × прогноз годовой выручки / 12

если вероятность убытка > 40%: rejected
иначе если вероятность кризиса ликвидности > 50%: rejected
иначе если чистая маржа < 1%: approved_with_discount, лимит × 0.5
иначе: approved
```

Лимит имеет ту же единицу, что годовая выручка: тысячи рублей. Например,
при прогнозе 120000 тыс. руб. базовый лимит равен 2000 тыс. руб.
Это воспроизведение правила исходного скрипта, не универсальная банковская
методика. При `rejected` код не обнуляет числовое поле лимита: интерпретируйте
его вместе с `decision`, а не как разрешённую сумму выдачи.

Месячные денежные потоки, DSCR, Долг/EBITDA и расчёты обслуживания долга
формируются отдельным финансовым кодом при достаточных исходных данных;
они не являются выходами этих пяти моделей. Поля `default_probability_percent`,
`approval_probability_percent`, `risk_grade` и
`operating_cash_flow_forecast_rub` данный ML-сервис оставляет `null`.

Итог LLM находится отдельно в `result.final_analysis`: `status`, `summary`,
`key_points`, `risks`, `missing`, `conflicts`, `next_steps`, `limitations`,
`provenance`, `not_a_decision=true`. Сбой этой сводки не должен уничтожать
детерминированные финансовые показатели. Ни LLM-сводка, ни поле рекомендации
ML `decision` не являются окончательным решением банка; его принимает сотрудник.

Все эти данные синтетические. Успешная обработка означает завершённый технический
сценарий, а не обязательное одобрение модели или банка. Метка mock в README
сама по себе не ставит её во все результаты обработки CSV.

## Другая LLM и сторонний API

### Другая модель в Ollama

Это поддерживаемый транспорт, но произвольная модель не обязательно умеет
Vision, русский финансовый текст и нужную JSON Schema. Проверьте совместимость
на тех же документах; отсутствие возможности должно давать явную ошибку или
`not_run`, а не придуманные финансовые данные.

1. Скачайте нужный существующий тег в Ollama ноды:

   ```powershell
   docker compose exec ollama ollama pull <новый-тег>
   docker compose exec ollama ollama list
   ```

2. В `.env` ноды добавьте `DOCUMENT_MODEL=<новый-тег>`. Одной записи недостаточно:
   исходный Compose не передаёт эту переменную контейнерам. В общий
   `x-environment: &environment` в `compose.yaml` добавьте:

   ```yaml
   DOCUMENT_MODEL: ${DOCUMENT_MODEL:-qwen3.5:35b-a3b}
   ```

3. `api/analysis_pipeline.py` и `api/tasks.py` уже читают `DOCUMENT_MODEL`;
   итоговый анализ получает ту же модель. Но `api/vision.py` задаёт тег жёстко.
   Чтобы заменить и Vision, добавьте туда `import os` и замените значение
   `"model": "qwen3.5:35b-a3b"` на
   `"model": os.getenv("DOCUMENT_MODEL", "qwen3.5:35b-a3b")`.
   Новая модель должна поддерживать изображения. Для текстовой модели оставьте
   прежний Vision или реализуйте отдельный `VISION_MODEL` и передайте его через
   Compose — такой отдельной настройки в исходной сборке нет.

4. Пересоберите и пересоздайте сервисы командой `up -d --build` с профилями
   `mock`, `ml` и теми же CPU/GPU/host override файлами, что при запуске.
   Менять только `restart` недостаточно. Запускатели по-прежнему проверяют и
   скачивают исходный тег; при окончательной миграции обновите также оба
   `start.sh`/`start.ps1` либо управляйте Compose вручную.

5. Проверьте текст, скан, JSON-контракт, единицы, лимиты контекста и завершение
   callback на новой задаче. Сохраните тег/версию и provenance результата.

Контракт Ollama `/api/chat`: `messages`, `model`, `format`, `stream=false`,
`options`; ответ читается из `message.content`, завершение — `done_reason=stop`.
Изображения передаются в `messages[].images` как base64. Сверяйте поддержку
конкретной модели с [официальной спецификацией Ollama](https://github.com/ollama/ollama/blob/main/docs/api.md).

### Ollama на отдельном сервере

Менять Django не нужно: он продолжает работать с DocumentNode. На ноде замените
жёсткое `OLLAMA_URL: http://ollama:11434` в `x-environment` на
`OLLAMA_URL: ${OLLAMA_URL:-http://ollama:11434}`, задайте в `.env` доступную базу
удалённого Ollama и пересоздайте сервисы. Модель скачайте **на удалённый** сервер.
В исходной сборке `api`/`worker` всё ещё зависят от локального сервиса `ollama`,
а start-скрипты проверяют его модель. Для полного исключения локального Ollama
измените также `depends_on` и запускатели; одной смены URL недостаточно.
Сетевой доступ и при необходимости авторизацию прокси настройте отдельно:
текущий клиент не добавляет ключ доступа к Ollama.

### Сторонний LLM API

Готового универсального переключателя на стороннего провайдера в этой версии нет.
Нельзя просто указать OpenAI-compatible `/v1` в `OLLAMA_URL`: код добавит
`/api/chat`, а тела запросов и ответов различаются.

Рабочий способ — добавить адаптер в DocumentNode, сохранив внешний контракт с Django:

1. Вынесите вызовы из `api/analysis_pipeline.py::_call_model`,
   `api/final_analysis.py::_post_chat` и `api/vision.py::vision_transcribe`
   в общий клиент провайдера. Выбор транспорта, URL, ключ и имя модели сделайте
   отдельными настройками, передаваемыми через Compose в `api` и `worker`.
   Это предлагаемая доработка, таких переключателей в архиве ещё нет.
2. По документации выбранного API преобразуйте system/user messages, JSON Schema,
   лимит ответа и изображения в его формат. Ключ передавайте только с сервера.
   Для текстового API оставьте отдельное распознавание сканов.
3. Приведите результат к внутренним `ExtractionResponse`, `FinalAnalysisContent`
   и контракту Vision `transcription`/`uncertain_fragments`. Например,
   Chat Completions-подобный API часто отдаёт текст в `choices[0].message.content`,
   тогда как Ollama — в `message.content`; точный контракт проверяйте у поставщика.
   Не возвращайте необработанный ответ провайдера в Django.
4. Обработайте отказ, обрезанный ответ, неверный JSON, timeout, 429 и 5xx;
   сохраните валидацию схем и границы повторов. Не подменяйте ошибки нулями
   или успешным расчётом. Маппинг `done_reason` также требует адаптации.
5. Сохраните текущие `/jobs`, `result.schema_version=2`, callback и feedback.
   Django не потребует изменений, пока эти контракты сохранены. Зафиксируйте
   имя модели/провайдера в provenance и проверьте тот же mock-набор на регрессии.

Альтернатива — отдельный gateway, который реализует используемые нодой
Ollama-совместимые `/api/chat` и `/api/tags`, а внутри обращается к поставщику.
Один лишь OpenAI-compatible endpoint этим требованиям не соответствует.
При внешнем API содержимое документов покидает локальный сервер: заранее
определите разрешённые данные и настройки хранения у выбранного поставщика.

## Проверка, диагностика и обслуживание

### Сквозная проверка после установки

1. Проверьте `docker compose ps` обоих проектов; у ноды добавьте профили
   `--profile mock --profile ml`, а для GPU — соответствующий `-f`.
2. Проверьте login Django, `/health` ноды, `/ready` ML и `/models` с ключом.
3. Создайте **новую** заявку через Django с реальными для теста файлами.
   Готовые заявки от `seed_demo` не проверяют связь с нодой.
4. В логах sender проверьте отправку и переход `NodeJob` в `WAITING`.
   Затем проверьте `GET /jobs/{job_id}` и `/delivery` ноды.
5. В Django должен появиться `COMPLETED` и результат нужной версии.
   Содержательный статус, готовность годовой модели, число полных месяцев
   и итоговая LLM-сводка проверяются отдельно.

| Симптом | Что проверить |
| --- | --- |
| Django 400 / DisallowedHost | Включён ли фактический Host, включая `django`/host gateway, в allowed hosts |
| Форма 403 CSRF | Origin с протоколом/портом; secure cookies только при HTTPS |
| Sender не запускается | `DOCUMENT_NODE_ENABLED=true`, непустые URL, API-ключ и callback-секрет |
| Нода 401 / 503 | Верный `X-API-Key` / ключ API задан в контейнере |
| Callback 401 / 503 | Совпадает отдельный callback-секрет / он задан в Django |
| Callback 404 | Адрес и job_id; возможна гонка регистрации задачи после 202 |
| Callback 409 | Другой JSON для уже сохранённого результата или несовместимый статус; разбирать вручную |
| Через nginx `/api/v1/llm/` даёт 404 | Ожидаемое закрытие внутреннего API |
| Соединение не устанавливается | Bind IP, firewall, адрес из контейнера; loopback не адрес другого контейнера |
| Долго нет результата | Логи worker, наличие модели, RAM/VRAM, очередь Redis; health API этого не исключает |
| `not_run` у ML | `ML_NODE_ENABLED`, `ML_NODE_URL`, полнота годовых входов, `missing_fields` |
| `failed` у ML | `ML_API_KEY`, readiness, соединение с `ml_node`, совместимость bundle |
| Мало полных месяцев | Подтверждение всех счетов, периода, остатков и полноты выписки |

Статусы sender: `PENDING → SENDING → WAITING → COMPLETED`, также `FAILED` и
`UNCERTAIN`. `COMPLETED` устанавливает callback. При таймауте отправки результат
может быть неизвестен: `UNCERTAIN` не пересылается автоматически, чтобы не создать
дубль. У `WAITING` нет автоматического таймаута; сверяйте задачу и доставку вручную.
Лимиты Django на загрузку могут быть шире ноды: принятие файла формой ещё не
означает, что sender сможет отправить >5 файлов, XLS или файл >10 MiB.

Логи из соответствующей папки:

```powershell
# Django:
docker compose logs --tail 100 django nginx
docker compose --profile node-sender logs --tail 100 node-sender
# DocumentNode, CPU; для GPU добавьте -f compose.yaml -f compose.gpu.yaml:
docker compose --profile mock --profile ml logs --tail 100 api worker callback_worker ml_node
```

Остановка с сохранением данных:

```powershell
# Django:
docker compose --profile node-sender stop
# DocumentNode, CPU:
docker compose --profile mock --profile ml stop
# DocumentNode, GPU:
docker compose -f compose.yaml -f compose.gpu.yaml --profile mock --profile ml stop
```

Не используйте `down -v` для обычной остановки: удалятся именованные volumes
с БД, документами, очередью или скачанными весами. У Django сохраняются
`postgres_data`, `media_data`, `static_data`; у ноды — `ollama_models`,
`redis_data`, `jobs_data`. Cleanup ноды имеет ограниченное хранение: в исходнике
заданы 24 часа для исходников и 7 дней для результатов/ошибок; это не архив
долговременного хранения. Для резервного копирования нужны БД Django и media,
настройки/секреты отдельно, а при необходимости — данные ноды и версии моделей.

### Django без Docker для разработки

Требуется Python ≥3.12. В `AlfaAmeba/`, PowerShell:

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -e ".[dev,analysis]"
$env:DJANGO_SETTINGS_MODULE="config.settings.dev"
.\.venv\Scripts\python.exe manage.py migrate
.\.venv\Scripts\python.exe manage.py seed_demo
.\.venv\Scripts\python.exe manage.py runserver 0.0.0.0:8080
```

На Linux используйте `.venv/bin/python` и `export DJANGO_SETTINGS_MODULE=config.settings.dev`.
По умолчанию dev использует SQLite; проверьте, что `DATABASE_URL` не указывает
случайно на другую БД. Для CSS нужен standalone Tailwind согласно основному
README проекта. Для внешней ноды в отдельном терминале того же окружения:

```powershell
.\.venv\Scripts\python.exe manage.py send_node_jobs --watch
```

Настройки `DOCUMENT_NODE_*` должны быть одинаковы в обоих процессах Django;
порт 8080 оставляет 8000 свободным для контейнерной ноды. `runserver` предназначен
для разработки; основной воспроизводимый запуск всего комплекта — Docker выше.
этого документа не запускались; это проверка инструкции по исходникам,
не протокол успешного развёртывания на новом сервере.
