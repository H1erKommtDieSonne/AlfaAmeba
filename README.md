# Умный кредитный кабинет

Веб-сервис кредитования бизнеса. Стек: Django templates, Tailwind CSS и Alpine.js.

## Текущее состояние

Сейчас реализован рабочий вертикальный срез:

1. представитель бизнеса регистрируется или входит по email;
2. бизнес выбирает кредитный продукт и заполняет короткую заявку;
3. Django проверяет условия продукта и создаёт запрос на подтверждение полномочий представителя организации;
4. отправленная версия сохраняется как неизменяемый JSON-снимок;
5. заявка появляется в закрытой очереди банковского кабинета;
6. кредитный специалист, старший согласующий и администратор банка получают разные рабочие разделы и права;
7. кредитный специалист берёт заявку в работу, оставляет клиентские или внутренние комментарии, возвращает её на доработку либо передаёт старшему согласующему;
8. клиент видит только предназначенные ему сообщения и отправляет новую неизменяемую версию после доработки;
9. старший согласующий принимает итоговое решение, а все изменения записываются в журнал событий;
10. банковские роли не могут создавать клиентские заявки.

Авторизация работает через защищённые сессии Django. Пароли сохраняются только в виде хешей. Обычная регистрация всегда создаёт представителя бизнеса. Указание ИНН не выдаёт доступ автоматически: членство создаётся только после ручного подтверждения администратором банка. Реализованы организации, запросы доступа, членство с ролями, очередь банка, карточка заявки, комментарии, доработка, согласование и аудит переходов.

Загрузка документов, pull-очередь для ML/LLM и отдельная очередь demo-аналитики уже реализованы. Документы забирает `ml-worker-documents`, результат аналитики — `ml-worker-analytics`. Оба воркера — детерминированные stub-заглушки: реальная модель, OCR, проверка организации, уведомления, PD и автоматическое кредитное решение не реализованы. Все демонстрационные данные синтетические. Текущий согласованный объём — gateway-срез; он не означает выполнения полного реального P0 из продуктового плана ниже.

### Рекомендация: изоляция клиентского и банковского контуров (не реализовано)

> Это рекомендация для будущей production-архитектуры, а не описание текущего демо. Сейчас клиентский и банковский интерфейсы работают на общем Django и одной базе данных; нижеописанное нигде не реализовано.

Для production рекомендуется разнести клиентский (публичный) и внутренний банковский контуры на отдельные сервисы, хосты и сетевые зоны. Клиентская БД не должна содержать учётные записи сотрудников и администраторов банка, их хеши паролей, MFA-секреты, сессии, токены восстановления, а также любые креденшелы для доступа к внутренней БД или панели. Изоляция распространяется на резервные копии и логи: секреты одного контура не должны попадать в другой через бэкапы или журналы.

- отдельные базы данных и отдельные DB-креденшелы для клиентского и внутреннего контуров, доступ по принципу минимальных привилегий;
- аутентификация банковских сотрудников — в изолированном или отдельном корпоративном identity-реалме, без репликации паролей и MFA между контурами;
- внутренний доступ — только через VPN и SSO с обязательным MFA;
- между контурами — только ограниченный аутентифицированный API для данных заявок, статусов и документов; никакого прямого доступа из клиентской БД к банковской;
- раздельные ключи подписи, ключи сессий и cookies для клиентского и внутреннего контуров.

### Жизненный цикл заявки

```text
SUBMITTED → IN_REVIEW → NEEDS_REVISION → SUBMITTED
                      ↘ PENDING_APPROVAL → APPROVED
                                         ↘ DECLINED
```

- кредитный специалист переводит новую заявку в `IN_REVIEW`;
- возврат клиенту требует поясняющего комментария;
- клиентская доработка создаёт следующую версию, не изменяя отправленные версии;
- итоговое одобрение или отклонение доступно только старшему согласующему;
- администратор банка управляет доступом и не видит очередь заявок;
- внутренние комментарии никогда не отображаются представителю бизнеса.

### Документы и demo-аналитика — текущий срез

Поток данных сервер-первый: браузер работает только с Django, а воркеры не получают пользовательских сессий и сами опрашивают внутренние pull-API Django по токену. Django — единственный источник заявок, файлов, статусов и результатов; воркеры не обращаются к браузеру, базе или файловому хранилищу напрямую.

1. При отправке или доработке Django в одной транзакции сохраняет версию заявки, документы с SHA-256, задачу `DocumentProcessingJob` и `AnalysisRun` в статусе `WAITING`.
2. `ml-worker-documents` забирает задачу из `/api/v1/llm/`, скачивает каждый файл через Django, проверяет размер и SHA-256 и возвращает по одному результату на документ.
3. После завершения (или окончательной ошибки) извлечения `AnalysisRun` становится доступен `ml-worker-analytics` через `/api/v1/analytics/`.
4. Аналитика возвращает строгий demo-результат `schema_version="1.0"`; Django проверяет его и сохраняет неизменяемый результат для конкретной версии заявки. В карточке банка показывается результат только текущей версии.

Сценарий `normal`, `missing_data` или `manual_review` задаётся на этапе извлечения документов (`DEMO_SCENARIO` у documents-воркера). Analytics-воркер не выбирает сценарий сам: он выводит его из `payload.scenario_id` полученных документов. Если извлечение не завершилось, документы пусты/неподдержаны или сценарии несогласованы, аналитика принудительно даёт `missing_data`, а не «нормальный» вывод.

Результат носит только информационно-демонстрационный характер: `is_demo=true`, OCR не выполнялся, реальная модель и PD не использовались, автоматического одобрения нет. Это не кредитное решение.

### Очередь документов для ML/LLM

При каждой первой отправке или доработке Django атомарно сохраняет:

1. неизменяемую версию заявки;
2. исходные документы с контрольной суммой SHA-256;
3. одну задачу `DocumentProcessingJob` в состоянии `PENDING`.

LLM-сервис работает по pull-модели и может опрашивать Django раз в минуту. Для него не используется пользовательская сессия или JWT: между внутренними сервисами передаётся отдельный секрет `LLM_SERVICE_TOKEN` в заголовке `Authorization: Bearer ...`.

```text
POST /api/v1/llm/jobs/claim/
GET  /api/v1/llm/jobs/{job_id}/documents/{document_id}/
POST /api/v1/llm/jobs/{job_id}/complete/
POST /api/v1/llm/jobs/{job_id}/fail/
```

Забрать следующую задачу:

```http
POST /api/v1/llm/jobs/claim/
Authorization: Bearer <LLM_SERVICE_TOKEN>
Content-Type: application/json

{"worker_id":"local-llm-1"}
```

Ответ `200` содержит снимок заявки, список документов, `job_id`, `lease_token` и время окончания аренды. Ответ `204 No Content` означает, что очередь пуста. Чтобы скачать файл, нужно передать оба служебных заголовка:

```http
Authorization: Bearer <LLM_SERVICE_TOKEN>
X-Lease-Token: <lease_token из claim>
```

После обработки воркер возвращает строго по одному сериализованному результату для каждого исходного документа. Текущая stub-реализация (`ml/stubs.py`) всегда помечает результат как демонстрационный, не выполняет OCR и кладёт синтетические fixture-факты:

```json
{
  "lease_token": "uuid из claim",
  "documents": [
    {
      "document_id": "uuid документа",
      "document_type": "demo_document",
      "schema_version": "1.0",
      "confidence": null,
      "payload": {
        "is_demo": true,
        "scenario_id": "normal",
        "extraction_method": "stub",
        "ocr_performed": false,
        "synthetic_fixture": true,
        "fixture_note": "Payload содержит только синтетические fixture-факты; они не извлечены из документа.",
        "verified_download": {"byte_count": 1234, "sha256": "..."},
        "fixture": {}
      }
    }
  ],
  "summary": {
    "document_count": 1,
    "is_demo": true,
    "extraction_method": "stub",
    "ocr_performed": false
  }
}
```

`payload.fixture` — вымышленные данные сценария, а не разбор файла; `payload.verified_download` подтверждает только совпадение размера и SHA-256 скачанных байтов.

Этот JSON отправляется на `POST /api/v1/llm/jobs/{job_id}/complete/`. При временной ошибке используется `POST .../{job_id}/fail/`:

```json
{
  "lease_token": "uuid из claim",
  "error": "Временная ошибка OCR",
  "retryable": true
}
```

`claim` выполняется с блокировкой строки базы. Задача выдаётся только одному воркеру на 10 минут по умолчанию. Если воркер пропал, аренда истечёт и задача снова станет доступной. После трёх неудачных попыток задача остаётся в `FAILED`. Интервалы задаются через `LLM_JOB_LEASE_SECONDS` и `LLM_RETRY_DELAY_SECONDS`.

В Docker этот API намеренно закрыт в Nginx и доступен LLM-контейнеру напрямую по адресу `http://django:8000/api/v1/llm`. При локальном запуске Django адрес будет `http://127.0.0.1:8000/api/v1/llm`.

### Очередь demo-аналитики

Отдельный внутренний pull-API аналитики использует собственный токен `ANALYTICS_SERVICE_TOKEN`. Токены очередей не взаимозаменяемы: запрос с `LLM_SERVICE_TOKEN` к аналитике (и наоборот) получает `401`.

```text
POST /api/v1/analytics/jobs/claim/
POST /api/v1/analytics/jobs/{run_id}/complete/
POST /api/v1/analytics/jobs/{run_id}/fail/
```

`claim` возвращает `job_id` (UUID запуска), `lease_token`, `input_hash`, документы с извлечёнными payload, `extraction_status`, `model_version` и `policy_version`; пустая очередь — `204 No Content`. `complete` принимает `lease_token`, `input_hash` и `result`; `fail` — `lease_token`, `error`, `retryable`. Запуск нельзя завершить, если входные данные изменились после выдачи задания.

Результат проверяется строгой схемой `schema_version="1.0"` в `analytics/services.py:validate_result`: фиксированный набор полей, `is_demo=true`, совпадение `model_version`/`policy_version` с запуском, допустимые `scenario_id`, `recommendation` и статусы четырёх компонентов (`evidence`, `radar`, `cashflow`, `scoring`). Полный перечень полей и ограничений — в этом валидаторе, а не в README; воркер собирает результат в `ml/stubs.py:build_analysis_result`.

`AnalysisRun` создаётся на каждую новую версию заявки, ждёт завершения извлечения, арендуется одним воркером и после `READY`/`PARTIAL` хранит неизменяемый результат. В банковской карточке показывается результат только текущей версии; он носит справочно-демонстрационный характер, не является кредитным решением и не содержит PD. Аренда и повторные попытки настраиваются через `ANALYTICS_JOB_LEASE_SECONDS` и `ANALYTICS_RETRY_DELAY_SECONDS`.

### Внешний узел проверки документов (опционально)

Интеграция с внешним узлом выключена по умолчанию и запускается только явным
профилем `docker compose --profile node-sender up -d`. Сервис `node-sender`
выполняет `python manage.py send_node_jobs --watch` на том же образе Django, с
той же БД и media, ждёт `django` healthy и использует сети `web` + `internal`.
Локальные demo-воркеры при этом не меняются.

Callback узла: `POST /api/v1/document-node/callback/` с отдельным
`Authorization: Bearer <DOCUMENT_NODE_CALLBACK_TOKEN>` (не `API_KEY`). Django
принимает только `"status": "completed"`, `job_id` из 32 hex-символов, `result`
объектом, `files` массивом и `verification_status` `needs_review` или
`not_verified`; дубль того же JSON даёт `200`, расхождение — `409`, неизвестный
`job_id` — `404`. Sender отправляет 1–5 файлов до 10 MiB, `.xls` не
поддерживается: банк может принять такую заявку, но задача узла станет
`FAILED`. При сетевой неопределённости задача получает `UNCERTAIN` и вручную
сверяется, без автоматической повторной отправки; без callback задача может
остаться в `WAITING` неограниченно долго. Полный контракт, LAN-настройки
`config.settings.lan`, адреса портов `8000`/`8080` и ограничения — в
[docs/document-node.md](docs/document-node.md).

### Кабинет сотрудника: финансовый анализ узла (схема v2)

Узел присылает в callback финансовый результат `result.financial_analysis` со
`schema_version: 2`: месячный денежный поток по выписке, годовые входы модели с
источниками, коэффициенты, сценарный прогноз остатка, запросы клиенту, рекомендации
сотруднику, предупреждения с `severity` и пустые слоты `model_outputs` под будущий
ML-сервис. Контракт — [docs/financial-api-v2.md](docs/financial-api-v2.md), JSON
Schema — [docs/schemas/financial-result-v2.schema.json](docs/schemas/financial-result-v2.schema.json)
(в копию добавлено необязательное `severity` у `warnings`), примеры узла —
`node_integration/fixtures/financial_v2/`.

Django хранит ответ как есть, а `node_integration/financial.py` превращает его в
данные для карточки: читает только известные поля с проверкой типов, поэтому новое
поле узла карточку не ломает, а ответ старой версии показывается как «старый формат».
Карточка заявки банка (`applications/templates/applications/bank/`):

- сверху ключевые цифры: запрошено, остаток по выписке, риск-грейд, готовность
  анализов, запросы клиенту;
- две колонки: «Что предоставил клиент» (задача, параметры, документы, годовая
  отчётность и извлечённые поля с источником и цитатой) и «Что выдал анализ»
  (выводы, сигналы с severity, коэффициенты, сценарии, вывод финмодели, что проверить);
- графики Chart.js: денежный поток по месяцам, прогноз остатка по трём сценариям,
  доли покупателей; цвета берутся из темы;
- замечания к документам (файл и страница) и «Что нужно от клиента» с кнопкой
  «Отправить фидбек клиенту»: заявка возвращается на доработку с редактируемым
  сообщением, собранным из запросов узла;
- «Что учла модель» и технические детали (подбор, сырой ответ узла, demo-аналитика)
  в сворачиваемом блоке.

В очереди банка кликабельна вся строка, а в карточке есть «Предыдущая / Следующая»
в порядке текущего фильтра очереди.

Узел считает только по тому, что получил в `application_context`. Контекст версии 2
несёт ИНН, тип кредита, сумму, срок, залог и дату расчёта, а то, что должен
подтвердить человек, вводит кредитный специалист в блоке «Данные для расчёта»:
ставка и платёж по новому кредиту (пусто — аннуитет), все расчётные счета клиента,
период и остатки каждой выписки, статус долгов, отчётный год. Сохранение ставит
версию на пересчёт — новая попытка `NodeJob` с новым `job_id`; пока узел считает,
карточка показывает прошлый результат с плашкой «идёт пересчёт». Годовую
отчётность ООО Django берёт сам из провайдера, если задан
`DOCUMENT_NODE_PROVIDER_URL`. Поля контекста — [docs/document-node.md](docs/document-node.md).

Без узла пересчёт остаётся «ждёт отправки»; на стенде с `DEBUG` ответить за узел
демо-результатом можно командой `python manage.py node_demo_complete`.

`seed_demo` создаёт две демо-заявки в работе у `bank@example.test` с готовым ответом
узла: оборотный кредит с полным комплектом и контрактный кредит, где не хватает
документов. Ответ собирает `node_integration/demo.py` по правилам контракта v2;
тест сверяет его со схемой. Повторный запуск `seed_demo` обновляет ответы, а не
создаёт новые заявки.

Chart.js 4.5.1 лежит в репозитории (`core/static/core/vendor/chart.umd.min.js`,
взят из npm-пакета, sha512 сверен с реестром) и подключается только на карточке
с готовым анализом.

## Первая публикация на GitHub

Создайте пустой репозиторий на GitHub, затем выполните из корня проекта:

```powershell
cd D:\Alfa_credit_scoring
git init
git add .
git status
git commit -m "Initial Django credit scoring application"
git branch -M main
git remote add origin https://github.com/USERNAME/REPOSITORY.git
git push -u origin main
```

Замените `USERNAME/REPOSITORY` на адрес своего репозитория. Перед коммитом проверьте через `git status`, что в список не попали `.env`, `.venv`, `tailwindcss.exe` и `credit_scoring.db`.

## Структура проекта

Устроено по образцу [knt-portal](https://github.com/Nepike/knt-portal): настройки разделены по окружениям, код — по приложениям. У каждого приложения свои `urls.py` (подключаются в `config/urls.py`), шаблоны в `<app>/templates/<app>/`, сервисы, админка и тесты.

| Приложение | Что в нём |
| --- | --- |
| `config` | Проект: `settings/base.py` (общее), `settings/dev.py` (разработка), `settings/prod.py` (Docker), `settings/lan.py` (демонстрационный LAN-стенд), корневые `urls.py` и `wsgi.py` |
| `core` | Общий каркас: `base.html`, фрагменты, страница 403, подсветка раздела в шапке (`nav.py`), статика и Alpine.js, `dashboard`, команда `seed_demo`, общая обвязка тестов |
| `users` | Своя модель `User`: вход по email без учёта регистра, поле `role`; вход, регистрация, проверки прав по роли (`users/permissions.py`) |
| `organizations` | Организации, членство с ролями, запросы доступа и их рассмотрение администратором банка |
| `products` | Каталог кредитных продуктов |
| `applications` | Заявки, неизменяемые версии, комментарии, журнал событий; кабинет бизнеса, очередь банка и демонстрационная карточка анализа текущей версии |
| `documents` | Документы версий заявки и pull-очередь извлечения для ML/LLM с API `/api/v1/llm/` |
| `analytics` | `AnalysisRun` на версию заявки, строгая схема demo-результата и внутренний pull-API `/api/v1/analytics/` |
| `ml` | Воркеры `ml.worker`, stdlib pull-клиенты очередей и детерминированные stub-заглушки `ml/stubs.py`; `ml/server.py` — прежний health-сервис `ml` |
| `node_integration` | `NodeJob`, опциональный sender `send_node_jobs --watch` и callback внешнего узла `/api/v1/document-node/callback/`; представление финансового результата v2 (`financial.py`) и демо-ответ узла (`demo.py`); подробности — [docs/document-node.md](docs/document-node.md) |

Окружение выбирает `DJANGO_SETTINGS_MODULE`: `manage.py` и `wsgi.py` по умолчанию берут `config.settings.dev`, Docker-образ — `config.settings.prod`, демонстрационный LAN-стенд — `config.settings.lan`. Переменные читаются через django-environ из окружения и из `.env` в корне проекта.

Фронтенд собирается без Node.js. CSS — standalone-бинарником Tailwind из `theme/input.css` в `core/static/core/css/app.css` (результат не коммитится). Alpine.js лежит в репозитории (`core/static/core/vendor/alpine.min.js`), компоненты — в `core/static/core/js/app.js`. Chart.js — там же (`chart.umd.min.js`), графики карточки сотрудника — в `core/static/core/js/charts.js`.

## 1. Что мы создаём

Веб-сервис для организаций и индивидуальных предпринимателей, который делает подачу кредитной заявки быстрой и простой, а рассмотрение — удобным для сотрудников банка. Финансовый директор, уполномоченный сотрудник или сам ИП регистрирует бизнес на платформе. В одной организации может работать один пользователь или много сотрудников с разными правами. После проверки сведений о бизнесе сервис помогает выбрать продукт и заполнить короткую заявку. Банк получает структурированные данные и предварительную аналитику, комментирует заявку, возвращает её на доработку или передаёт старшему сотруднику на одобрение.

Первый демонстрационный сегмент из прежнего плана — торговые ИП с эквайрингом, основной сценарий — оборотный кредит. Общая концепция шире: организации с финансовым директором и командой также входят в целевую модель. Сохраняем два кабинета и каталог из двух продуктов; второй продукт ещё нужно выбрать. Начинаем с одного банка.

Идея продукта: **быстро и просто подать качественную заявку со стороны бизнеса и сократить ручную работу при её рассмотрении со стороны банка**.

Это уточнение сути сервиса дано пользователем 20 октября 2026 года и определяет приоритет интерфейсов и процесса. Проверки, Risk Radar, денежный расчёт и ML поддерживают этот путь. Клиенту показываем короткие понятные рекомендации; подробная аналитика доступна сотруднику банка и по необходимости клиенту.

### 1.1. Основные принципы — уточнение пользователя

- Одна компания — общее рабочее пространство для одного или многих сотрудников, а не отдельная несвязанная компания на каждый аккаунт.
- Проверка данных компании/ИП предшествует полноценной подаче. Конкретные уровни проверки и полномочий ещё предстоит определить; в демо они синтетические.
- Начальная заявка максимально простая. Уже известные сведения подставляются с возможностью проверки, дополнительные поля и документы запрашиваются по необходимости.
- Продукты рекомендуются по параметрам бизнеса и потребности; популярные кредиты могут быть дополнительным ориентиром. Популярность показывается отдельно от соответствия конкретному бизнесу и не означает доступность или одобрение.
- Подсказки по заполнению используют прошлые корректировки и просьбы сотрудников банка по похожим заявкам: помогают предупредить типовые возвраты до отправки.
- Сотрудник банка видит данные, предварительные предсказания и причины подсказок, добавляет комментарии и выбирает следующий шаг.
- Предусмотрены возврат клиенту на доработку и передача старшему сотруднику банка на одобрение. Полномочия и итоговое решение остаются у людей.

### 1.2. Как измеряем основную ценность

Предлагаемые метрики: время до первой отправки заявки, доля завершённых заявок, число циклов доработки, активное время сотрудника на рассмотрение, время до передачи на одобрение и итогового ответа. Отдельно проверяем качество: долю существенных пропусков и ошибочных подсказок. Ожидание ответа клиента отделяем от времени работы банка. Базовые значения и целевые улучшения устанавливаем после замеров; ускорение не должно достигаться пропуском необходимых проверок.

Это план, а не отчёт о реализованных возможностях. Основа — два предоставленных Markdown-файла и ссылка на TLSNotary. Уточнения от 20 октября в исходном роадмапе считаем актуальнее ранних примеров: 6 дней, 5 участников, синтетические банковские данные и сервисы, допустима RTX 4090. Сроки и состав команды здесь перенесены из документа, а не подтверждены заново.

Обозначения происхождения идей:

- **Из материалов** — идеи и договорённости из предоставленных файлов; внутри них уже были предложения предыдущих обсуждений.
- **Уточнение пользователя** — непосредственно описанная пользователем основа сервиса; имеет приоритет перед более ранними формулировками концепции.
- **Новая идея** — предложения, добавленные при подготовке этого общего плана; они ещё не приняты командой.

## 2. Главный пользовательский сценарий

1. Финансовый директор, уполномоченный сотрудник или ИП регистрирует организацию. Коллеги присоединяются к её рабочему пространству с назначенными правами; для ИП достаточно одного пользователя.
2. Сервис проверяет сведения компании/ИП и показывает результат, обнаруженные несоответствия и необходимые уточнения. В демо используются локальные синтетические проверки.
3. Пользователь указывает цель, сумму и срок. Сервис предлагает продукты по параметрам бизнеса и отдельно может показывать популярные варианты с понятным основанием рекомендации.
4. Пользователь заполняет короткую заявку с предзаполненными известными сведениями. Простые подсказки учитывают типовые замечания банка к похожим прошлым заявкам.
5. При необходимости пользователь загружает выписку PDF/CSV. Локальная модель извлекает кандидаты фактов; сервер проверяет их, пользователь подтверждает неоднозначные значения. Не требуем весь пакет документов до начала заполнения.
6. После отправки банк получает снимок заявки, сведения бизнеса, результаты проверок, предварительные предсказания и расчёт денежного потока. Сотрудник видит источники фактов и пробелы.
7. Сотрудник комментирует заявку и возвращает её на доработку либо готовит заключение и передаёт старшему сотруднику на одобрение. Клиент получает только предназначенные ему замечания.
8. При доработке клиент исправляет конкретные поля или добавляет сведения. Создаётся новая версия; сотрудник видит, что изменилось и какие замечания закрыты.
9. Старший сотрудник рассматривает актуальную версию и заключение: утверждает условия, отклоняет заявку либо возвращает её сотруднику с замечаниями. Если нужны сведения клиента, сотрудник оформляет новый запрос.
10. Клиент получает итоговое объяснение или предложение, сравнивает условия и принимает действующее предложение либо отказывается. Подписание и выдача имитируются с отметкой demo.

На каждом экране видны статус и следующее доступное действие. Внутреннее обоснование банка отделено от объяснения для клиента.

| Risk Radar | Какие внешние факты требуют внимания? | Балл радара не является вероятностью дефолта |
| Денежная выполнимость | Хватит ли денег на обязательства при данных сумме и сроке? | Положительный расчёт не гарантирует одобрение |
| Табличный ML | Как модель оценивает симуляционный риск данного кредита? | Качество на синтетике не доказывает качество на реальных клиентах |

Итоговое решение принимает уполномоченный сотрудник банка с учётом продуктовых правил; основной сценарий включает согласование старшим сотрудником. LLM извлекает сведения и помогает формулировать объяснения, но не назначает условия и не принимает решение.

## 4. Функциональные блоки

### 4.1. Кабинет бизнеса и кабинет банка — из материалов

- Пользователи, организации и членство: несколько представителей одной компании; банковские роли назначаются отдельно.
- Каталог продуктов с версиями правил, ограничениями, документами и сроками действия условий.
- Черновик, постепенное заполнение, подсказки, отправка и неизменяемый снимок заявки.
- Загрузка документов, конкретные уточнения, ответы и уведомления внутри кабинета.
- Очередь банка, карточка заявки, сводка, внутренние комментарии и клиентские сообщения.
- Решение с кодами причин; альтернативные сумма, срок или продукт; срок действия предложения.
- История изменений, повторная заявка, имитация подписания и выдачи.

Уточнение пользователя: в банковском кабинете нужны роли рассматривающего и старшего сотрудника, очередь согласования, заключение и возврат с замечаниями. Это роли внутри одного банковского кабинета. В компании предлагаем различать администратора, редактора заявки и пользователя с правом отправки; один человек может совмещать роли. Конкретная матрица прав ещё согласуется. Регистрация записи компании сама по себе не подтверждает полномочия её представителя.

### 4.1.1. Простые рекомендации из опыта банка — уточнение пользователя

Сохраняем связь: версия заявки → замечание сотрудника → затронутое поле/документ → исправление → результат повторной проверки. На основе повторяющихся замечаний формируем короткие подсказки для похожих заявок. Предлагаемые признаки сходства: продукт, цель, вид бизнеса, масштаб оборота и состав предоставленных сведений; конкретный набор проверяем на данных.

Пример подсказки: «Укажите, на какой период нужна закупка товара: это поможет банку оценить сумму». Она объясняет одно действие и появляется у соответствующего поля. Клиент не должен читать внутреннее заключение или разбираться в скоринговых терминах.

Для MVP предлагаем небольшой каталог проверенных подсказок, построенный на синтетической истории замечаний и исправлений. Правила выбирают подходящую подсказку; локальная LLM может помогать с формулировкой по проверенному содержимому. Переобучение модели после каждого комментария не требуется. В дальнейшем сравниваем подсказки с фактическим уменьшением возвратов и учитываем, помогло ли исправление закрыть замечание.

Замечания не копируем автоматически: проверяем актуальность продуктовых правил, применимость к новой заявке и повторяемость причины. Пользователь не видит сведения других компаний и внутренние комментарии. При отсутствии релевантной истории используем общие проверенные подсказки и не изображаем персонализацию. Рекомендации по продуктам и рекомендации по заполнению — отдельные механизмы с отдельными основаниями.

### 4.2. Документы и локальная LLM — из материалов

Начинаем с одной формы выписки и ограниченного набора PDF/CSV. Используем готовую модель с открытыми весами; дообучение LLM в первой версии не требуется. Конкретные модель, размер и режим запуска выбираем по фактическим замерам на доступной машине.

Модель возвращает строгий JSON с кандидатами фактов и ссылками на источник: документ, поле, страницу/координаты либо строку CSV, владельца и период. Backend валидирует схему и значения; денежную арифметику выполняет код. Неоднозначность приводит к уточнению, а не к выдуманному значению.

Для каждого документа отдельно рассматриваем читаемость, согласованность, принадлежность и подлинность. Совпадение реквизитов не доказывает подлинность. Несколько документов на одном фото, рукопись и иностранные паспорта — расширение после устойчивого основного сценария; документы и поля разных экземпляров нельзя смешивать.

Основной процесс должен сохранять работоспособность при ошибке LLM через ручное подтверждение/ввод и правила. При этом критерий нашего полного демо включает реальный локальный вызов модели, а не только заглушку.

### 4.3. Денежный расчёт и карта условий — из материалов

- Основная история — 12 месяцев; неполный период явно отображается.
- Собственные переводы и дубли не увеличивают выручку. Неизвестный долг не подставляется как ноль.
- Учитываем существующие обязательства, сумму нового кредита, срок и платёж.
- Помесячно рассчитываем остаток и резерв в базовом и стрессовом сценариях; показываем минимальный остаток и ограничивающий месяц.
- Карта «сумма × срок» сравнивает варианты. В MVP достаточно таблицы вместо сложной визуализации.
- При изменении фактов, условий, политики или модели создаём новый расчёт; старый сохраняем и помечаем как относящийся к прежней версии.

Параметры стресса и минимального резерва — демонстрационные настройки с описанием, а не нормативы банка. Деньги считаем через Decimal или целые минимальные единицы.

После MVP: обратный стресс-тест — какое ухудшение нарушит резерв; две допустимые трактовки спорной операции и сравнение их последствий. Это анализ чувствительности, а не доказательство причинного снижения риска.

### 4.4. Следующий полезный документ — из материалов

Выбираем запрос по трём основаниям: пробел в данных, влияние на вывод, усилия клиента. Отсутствующий документ не означает высокий риск. Запрос должен объяснять, какое неизвестное он разрешит; недоступный документ должен иметь понятный дальнейший маршрут.

Сравниваем наш алгоритм с тремя базовыми стратегиями: полный фиксированный пакет, фиксированные узкие запросы, случайный порядок. Используем одинаковые синтетические случаи, ограничения бюджета запросов и случаи недоступности документов.

Измеряем число запросов, условные затраты пользователя, долю разрешённых существенных пробелов и корректность итогового вывода относительно синтетической истины. Формулу затрат, бюджет и критерии сравнения фиксируем до эксперимента. Не обещаем снижение числа запросов без измерений.

### 4.5. Табличный ML и обучение — из материалов

В полном P0 обучаем простую модель на синтетических историях и исходах: logistic regression как baseline; CatBoost как возможный кандидат. Риск связан с конкретными суммой, сроком и платежом, а не только с портретом компании. Сохраняем генератор, seed, признаки, manifest набора, версии и отчёт о калибровке.

Разделяем данные по бизнесам и времени; версии одной заявки не должны попадать одновременно в обучение и проверку. Не используем сведения из будущего. Прямые идентификаторы исключаем из признаков. Метрики выбираем по задаче: калибровка и log loss для вероятностей, precision/recall для причин уточнений, качество ранжирования для выбора продукта.

Решения сотрудников и фактическое погашение — разные цели обучения. Одобрение не является меткой надёжности; по отклонённым заявкам обычно нет наблюдаемого погашения. Фиксируем, видел ли сотрудник рекомендацию модели, чтобы учитывать влияние подсказок на последующие решения.

На развитие сохраняем цикл: накопление допустимых данных → проверка достаточности → обучение кандидата → сравнение с baseline и рабочей моделью на одном отложенном наборе → проверка сегментов, скорости и ошибок → теневой запуск → решение ответственного → переключение с откатом. Возможное расписание проверки — еженедельно, но календарь сам по себе не является основанием заменить модель. Каталог ставок и правил обновляется отдельно от обучения.

### 4.6. Risk Radar и внешние данные — из материалов

Сохраняем каталог из 23 источников/наборов данных как целевое покрытие, а не обещание подключить 23 интеграции за хакатон. Несколько наборов относятся к одному ведомству или порталу. Это собственный прозрачный каталог из предоставленного файла, а не подтверждённый список источников Сбера.

Для MVP используем пять локальных адаптеров: RegistryProvider, FinancialsProvider, LegalRiskProvider, ContractProvider и CollateralProvider. Отдельно — CreditHistoryProvider для синтетической кредитной истории. Полный каталог и демонстрационные правила приведены в приложении A.

Для каждой проверки храним источник, дату сведений, время получения, версию адаптера, проверенную версию заявки и статус. Для радара: OK, NO_DATA, UNAVAILABLE, MANUAL_REVIEW; для БКИ: OK, NO_HISTORY, UNAVAILABLE, INVALID_REQUEST. Таймаут и отсутствие данных не равны отрицательному результату.

**Предлагаемое уточнение:** применимость источника хранить отдельным признаком. Для стартового сегмента ИП нельзя ожидать тот же комплект отчётности, что для юридического лица; неприменимый источник не должен создавать штраф за отсутствие данных.

Сильные флаги запрещают автоматическое одобрение и направляют на рассмотрение сотруднику. В исходном каталоге для прекращённой компании допускался отказ либо ручная проверка; для общего демо предлагаем единый маршрут через сотрудника с объяснением. Числовой балл не отменяет стоп-флаг.

Реальные БКИ, банковские транзакции и закрытые рейтинги не доступны только по ИНН. Договоры, основания доступа, условия хранения и использования для обучения проверяются отдельно при переходе к пилоту. Собственная база заявок не становится собственным бюро кредитных историй.

### 4.7. TLSNotary — исследование по новой ссылке

TLSNotary описывает протокол подтверждения происхождения данных TLS-сессии и их неизменности с выборочным раскрытием содержимого. Официальная страница также описывает MPC и указывает тестовый alpha-статус. Это основание для ограниченного прототипа, а не обещание готовой банковской интеграции. [Источник: TLSNotary About](https://tlsnotary.org/about/), просмотрено 20.10.2026.

**Наша гипотеза применения:** клиент подтверждает отдельные сведения из своего веб-кабинета, раскрывая банку только нужные данные. Возможные кандидаты — отчёт эквайринга или обороты, если конкретный источник технически совместим и такой сценарий допустим.

Предлагаемый отдельный PoC после P0:

1. Выбрать контролируемый тестовый HTTPS-источник с синтетическими сведениями и заранее определить раскрываемые поля.
2. Проверить совместимость и доверительную модель выбранной версии TLSNotary, роли prover/verifier/notary и требования к инфраструктуре.
3. Получить и проверить настоящее доказательство; показать, что изменённые данные проверку не проходят.
4. Привязать результат к заявке, источнику, субъекту и периоду; отдельно спроектировать проверку свежести и защиту от повторного использования.
5. Проверить, какие сведения видит каждая сторона, размеры доказательств, задержку и возможность воспроизвести эксперимент.

Успех PoC: подлинное доказательство для тестового источника, обнаружение подмены и понятный перечень ограничений. JSON-заглушка не считается интеграцией TLSNotary.

**Границы нашей гипотезы:** доказательство происхождения не устанавливает экономическую истинность записи, полноту всех счетов, личность заёмщика или кредитоспособность. Принадлежность аккаунта, период, свежесть и правила раскрытия проверяются отдельно. Возможность доказать агрегат без раскрытия операций, включая ZK-подходы, требует самостоятельного исследования; в MVP её не обещаем. TLSNotary не заменяет БКИ, согласия или договорные API.

В шестидневный обязательный объём TLSNotary не включаем. Текст этой секции описывает предлагаемое использование, а не уже работающую возможность проекта.

## 8. Архитектура и данные — предлагаемая основа из материалов

Модульный монолит: React + TypeScript, FastAPI, PostgreSQL, файловое хранилище и Docker Compose. Стек остаётся предложением; существующий выбор команды имеет приоритет. Версии фиксируем после проверки совместимости. Локальный inference выделяем в отдельный процесс, если этого требуют зависимости или GPU.

Модули: identity, organizations, products, applications, documents, workflow, checks, decisions, notifications, audit, recommendations. UI получает данные через API; источник истины о состоянии — БД.

Основные сущности: User, Organization, Membership; Product/ProductVersion; Application/ApplicationVersion; Document; CheckRun; ClarificationRequest/Message; Decision/Offer; AuditEvent/Recommendation/ModelVersion. Проверка и расчёт всегда привязаны к версии заявки. В снимке прогноза сохраняются признаки, продукт, политика, модель и последующее решение.

Дополняем сущности: OrganizationVerification для проверки бизнеса; ReviewComment с полем/документом, видимостью и состоянием разрешения; ApprovalRequest с заключением, автором, согласующим и версией заявки; Hint/HintVersion и события показа подсказки с её основанием. Историю исправлений связываем с замечаниями и исходной версией.

Переходы: DRAFT → SUBMITTED → CHECKING → UNDER_REVIEW. Из рассмотрения — NEEDS_INFO либо PENDING_APPROVAL. После ответа клиента создаётся новая версия и выполняются CHECKING → UNDER_REVIEW. Из PENDING_APPROVAL старший сотрудник утверждает предложение (OFFERED), отказывает (REJECTED) или возвращает сотруднику (UNDER_REVIEW). Утверждение относится к конкретным версии заявки и условиям; изменение после передачи требует повторного согласования. Возможность отказа обычным сотрудником вне этого маршрута пока не включаем: её необходимо отдельно определить в матрице полномочий. Предложение можно принять, отклонить или дождаться истечения срока. После ACCEPTED — SIGNED_DEMO → DISBURSED_DEMO. До принятия возможна отмена. После отказа повторная подача создаёт связанную заявку; прежнее решение сохраняется.

Группы API: сессии и текущие права; регистрация/проверка организации и управление участниками; продукты и подсказки; черновики/отправка; загрузка/скачивание документов; очередь банка; комментарии/уточнения/ответы; передача на согласование и очередь старшего сотрудника; решения; принятие/отклонение предложений; demo-подписание/выдача; история. До реализации фиксируем JSON-схемы и OpenAPI. Ошибки содержат code, message, field_errors, request_id без внутренних трассировок.

Общие требования реализации:

- Сервер проверяет роль, компанию и право на каждый объект; фильтрации списка недостаточно.
- Решение и смена статуса атомарны; номер версии защищает от гонок; повторные действия идемпотентны.
- Устаревшие, отозванные и заменённые предложения нельзя принять.
- Пароли хешируются; сессии ограничены; предусмотрена защита от перебора. Для cookie — HttpOnly, SameSite, CSRF-защита, Secure в HTTPS.
- Файлы имеют ограничения типа/размера, собственные имена и защищённое скачивание; их содержимое не исполняется.
- Входные документы и комментарии — данные, а не команды для LLM. Секреты не попадают в клиент и репозиторий.
- Время хранится с часовым поясом; валюта и единицы расчёта явны. Логи не содержат полные документы.
- В демо только синтетические сведения. Для пилота отдельно проектируются хранение, удаление, согласия и аудит доступа.

## 10. Приёмка и демонстрация

Обязательные сценарии:

1. Полный путь: регистрация и проверка бизнеса → короткая заявка с подсказкой → рассмотрение → замечание → исправление и новая версия → согласование старшим сотрудником → предложение → принятие → demo-оформление и выдача.
2. Отказ с клиентским объяснением и отдельным внутренним обоснованием.
3. БКИ/источник недоступен: незавершённая проверка и повтор без ложного отказа.
4. Прямой запрос чужой заявки, документа или внутренней заметки запрещён сервером.
5. Повторная отправка, конкурентное решение и принятие старого предложения не портят данные.
6. Перезапуск сохраняет версии и историю; чистая установка воспроизводит демо без сети.
7. Реальный локальный LLM-вызов возвращает проверяемые факты; неоднозначность не превращается в выдумку.
8. Собственные переводы/дубли исключены, неизвестный долг не равен нулю, смена условий инвалидирует актуальность прежнего расчёта.
9. ML-отчёт воспроизводим, разделение данных корректно; стратегии запросов сопоставлены на одинаковых условиях.
10. Один ИП работает самостоятельно; у организации несколько пользователей с разными правами видят общее пространство, а действия каждого отражены в истории.
11. Обычный банковский сотрудник не утверждает решение за старшего; старший может вернуть заявку с замечанием. Устаревшую версию согласовать нельзя.
12. Подсказка у поля основана на релевантном прошлом замечании и не раскрывает чужие сведения; при отсутствии истории применяется общая подсказка. Популярный продукт не обозначается как уже одобренный.

Проверки: модульные для расчётов/правил/переходов; интеграционные для прав, транзакций, идемпотентности, миграций и адаптеров; сквозной главный сценарий в браузере. Для цикла моделей — воспроизводимость, отсутствие утечки и откат. Проверки должны подтверждать поведение, а не повторять реализацию.

Комплект сдачи: репозиторий с фиксированным commit hash, конфигурация запуска, lock-файлы, модели и лицензии, README с демоаккаунтами, OpenAPI, описание схемы и ограничений, синтетические сценарии, отчёты экспериментов, THIRD_PARTY_NOTICES. Требования к публичности и тегу alfa-hack-2026 перепроверяем по исходному заданию: сам конкурсный PDF для этого объединения не предоставлен.

Порядок защиты: проблема долгого заполнения и повторных возвратов → регистрация бизнеса → простая заявка с полезной подсказкой → карточка сотрудника с данными и прогнозами → конкретное замечание и исправление → согласование старшим → предложение клиенту. Затем показываем измеренные время заполнения и трудозатраты рассмотрения, сравнение стратегий и ограничения. TLSNotary, если прототип появится, демонстрируем отдельно.

1. Интервью с бизнесом и сотрудниками банка: время заполнения, завершение анкет, возвраты, первый ответ и ошибки. Эффект подтверждаем сравнением с зафиксированной базой.

4. Наблюдение фактического погашения и самостоятельная валидация риск-модели; мониторинг дрейфа, качества и причин отката.
5. Повторные заявки с актуализацией документов; аналитика банковской очереди; поиск похожих случаев с проверкой прав и действующих правил.
6. Многобанковский режим с маршрутизацией, согласиями и изоляцией банков.
7. Расширение документов, KYC/KYB, при необходимости NFC/биометрии; mock KYC не подтверждает реальную личность.

### Модель расчёта Risk Radar для демо

Начальный балл: **10 из 10**. Каждое правило уменьшает балл, но не ниже 1.

| Флаг | Изменение балла | Действие процесса |
| --- | --- | --- |
| Компания прекращена / ликвидация | Стоп-флаг | Отказать с объяснением или направить сотруднику |
| Банкротная процедура | Стоп-флаг | Направить сотруднику; не делать автоодобрение |
| Недостоверные сведения или дисквалифицированный руководитель | −4 | Запросить уточнение и ручную проверку |
| Налоговая задолженность | −2 | Запросить подтверждение урегулирования |
| Исполнительное производство | −2 | Ручная проверка суммы и статуса |
| РНП | −3 | Ручная проверка / ограничение контрактного продукта |
| Бизнес младше 12 месяцев | −1 | Запросить дополнительное обеспечение или документы |
| Убыток или падение выручки | −1…−2 | Запросить выписку и прогноз денежных потоков |
| Активный статус, МСП, стабильная отчётность | 0 | Положительные факторы показываются, но балл не «накручивается» |

Баллы демонстрационные и не являются условиями банка. Результат нужно показывать с датой проверки, перечнем сработавших фактов, версией правил и статусом каждого источника: `OK`, `NO_DATA`, `UNAVAILABLE` или `MANUAL_REVIEW`.
