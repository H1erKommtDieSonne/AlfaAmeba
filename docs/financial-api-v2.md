# Финансовая подготовка документов — API v2

База ноды: `http://192.168.1.105:8000`. [Swagger](http://192.168.1.105:8000/docs).
Все рабочие endpoints требуют `X-API-Key`; `/health`, `/docs`, `/openapi.json`
доступны без ключа. Секреты не включаются в примеры и результаты.

Нода проверяет документы, извлекает наблюдения с источниками, готовит входы
моделей, считает коэффициенты и простой месячный прогноз. Она **не запускает
`predict_application.py`**, не выдаёт кредитное решение и не отправляет
сообщения клиенту напрямую. Django показывает сформированные запросы клиенту
и сотруднику и управляет версиями/статусами заявки. Инференс годовых
ML-моделей — отдельный опциональный шаг узла (`POST /v1/predict`), а не
действие Django: см. [контракт инференса](ml-inference-contract.md).

## Endpoints

| Метод и путь | Принимает | Возвращает |
| --- | --- | --- |
| `POST /jobs` | Multipart: `files`, `application_context`, необязательный `system_prompt` | HTTP 202: `job_id`, `status: queued`, `files_count` |
| `GET /jobs/{job_id}` | ID из ответа `/jobs` | Состояние RQ либо сохранённый результат с `result.schema_version: 2` |
| `GET /jobs/{job_id}/delivery` | ID задачи | Наличие сохранённого результата и подтверждения callback/feedback |
| `POST /analyze` | Тот же multipart | Тот же результат v2 сразу, без `job_id`, очереди и callback |
| `POST /financial/prepare` | JSON: `application_context` и `financial_data` | Непосредственно объект `AnalystResult`, без внешнего `result` |
| `GET /financial/schema` | Только ключ | JSON Schema контекста, извлечения, запроса подготовки и результата |
| `GET /health` | Без ключа | `{"status":"ok"}` |
| `GET /models` | Только ключ | Список доступных моделей Ollama |

`/financial/prepare` выполняет только расчёты над уже структурированными данными:
не вызывает LLM, не скачивает отчётность, не читает файлы, не проверяет наличие
контракта/права собственности. Для проверки комплекта используйте `/jobs`
или `/analyze`.

## Полный рабочий пример

Каталог [examples/financial-v2](../examples/financial-v2/) содержит:

- `context.json` — контекст со сведениями mock-провайдера и параметрами заявки;
- `bank.csv` — операции по счёту за июль–сентябрь 2026;
- `prepare-request.json` — готовое тело `POST /financial/prepare`;
- `financial-result.json` — полный финансовый результат;
- `node-result.json` — пример результата проверки комплекта;
- `node-result-needs-documents.json` — пример запросов контракта и обеспечения.

Все примеры синтетические, расчётная дата зафиксирована: `2026-10-24`.
Перегенерация без обращения к LLM: `python examples/financial-v2/generate_examples.py`.

Отправить документы:

```sh
curl -X POST 'http://192.168.1.105:8000/jobs' \
  -H "X-API-Key: $API_KEY" \
  -F 'files=@examples/financial-v2/bank.csv' \
  -F 'application_context=<examples/financial-v2/context.json'
```

Сохранить `job_id` и опрашивать:

```sh
curl 'http://192.168.1.105:8000/jobs/JOB_ID' -H "X-API-Key: $API_KEY"
```

Подготовить данные без очереди и распознавания:

```sh
curl -X POST 'http://192.168.1.105:8000/financial/prepare' \
  -H "X-API-Key: $API_KEY" -H 'Content-Type: application/json' \
  --data-binary @examples/financial-v2/prepare-request.json
```

## Контекст заявки

`application_context` в multipart — **строка с JSON-объектом**, до 64 KiB после
нормализации. В `/financial/prepare` это обычный вложенный JSON-объект.
Основные поля:

| Поле | Назначение |
| --- | --- |
| `application_id`, `document_version` | Связать результат с той же заявкой и конкретным комплектом |
| `borrower_inn` | ИНН заявителя; значения другого лица исключаются |
| `loan_type` | `working_capital`, `contract`, `investment`, `refinancing` |
| `loan_amount_rub`, `term_months`, `annual_rate_percent` | Метаданные заявки для карточки сотрудника |
| `has_collateral` | Нужны документы о собственности и отдельно оценочная стоимость |
| `contract_appendices_required` | Требовать предусмотренные контрактом приложения |
| `reporting_year` | Год входов годовой модели; иначе выбирается последний полный год из источников |
| `analysis_date` | Дата расчёта; по умолчанию календарная дата сервера, для воспроизводимости задавайте явно |
| `forecast_month` | Необязательный `YYYY-MM`; по умолчанию следующий календарный месяц после `analysis_date` |
| `expected_account_ids` | Подтверждённый банком список всех расчётных счетов |
| `provider_reports` | Массив ответов mock-bo `/metrics` с метаданными, а не голый `/scoring-input` |
| `financial_data` | Подтверждённые структурированные наблюдения, дополняющие извлечение из файлов |
| `statement_periods` | Для CSV: полный период, счёт, начальный/конечный остатки и подтверждение `complete` |
| `debt_schedule_complete`, `debt_schedule_start/end` | Подтверждение полноты всех долговых графиков на диапазоне дат |
| `no_existing_debt_confirmed` | Явное подтверждение отсутствия действующих долгов на расчётном диапазоне; не выводится из отсутствия файлов |
| `proposed_monthly_payment_rub` | Платёж по запрашиваемому кредиту из расчёта банка; неизвестный платёж остаётся `null` |

Поля подтверждения полноты задаёт сервер/сотрудник после проверки, а не LLM.
Без списка счетов нода не утверждает, что видит весь денежный поток бизнеса.
Пустой список графиков не означает отсутствие долга.

Встроенная проверка продукта требует выписку; для контрактного кредита —
контракт и приложения при `contract_appendices_required=true`; для
инвестиционного — смету ИЛИ предложение; для рефинансирования — договоры,
графики, остатки; при залоге — подтверждение собственности. Финансовые
запросы дополняют этот перечень только для недоступных видов анализа.

## Данные провайдера и документов

Для ООО Django может получить
`GET http://192.168.1.105:8010/api/v1/organizations/9900000017/metrics?year=2025`
и передать **весь объект** в `application_context.provider_reports`.
Нода не ходит по произвольным URL из контекста. Данные провайдера и документов
сопоставляются по ИНН, периоду, единицам. При конфликте источник не выбирается
молча: поле становится `null`, сотрудник получает предупреждение.

`financial_data` имеет пять массивов (все необязательны):

| Массив | Содержание |
| --- | --- |
| `annual_metrics` | `field`, `value`, явный `unit`, фактический период/дата, `source` |
| `cash_flow_months` | Отдельный месячный итог каждого счёта, покрытие и `complete_month`, остатки/движения/классификация |
| `debt_payments` | `loan_id`, `due_date`, `unit`, `total_payment` и/или известные составляющие `principal`, `interest`, `fees` |
| `supplemental_metrics` | `ebitda`, `total_debt`, `cfads`, `collateral_value` с единицами, датами/периодами |
| `document_fields` | Дополнительные поля карточки: `name`, `value`, `unit`, `source` (например, номер/дата договора, кадастровый номер) |

У неизвестных составляющих платежа значение `null`, а не ноль. Если известен
общий платёж, его можно передать без выдуманной разбивки. При неизвестном
общем платеже и неполной разбивке обслуживание долга не рассчитывается.

Каждое наблюдение содержит `source`:

```json
{
  "filename": "balance.pdf",
  "provider": null,
  "locator": "страница 2, строка 1600",
  "quote": "1600 Баланс 60 000",
  "is_mock": false
}
```

Для извлечённых LLM значений цитата должна дословно присутствовать в текущем
фрагменте файла; неизвестные имена файлов, выдуманные цитаты и ссылки на
провайдер вместо файла исключаются. Это проверка опоры на текст, **не проверка
подлинности документа или правильности финансовой интерпретации**. Проценты
уверенности моделью не сочиняются; сотрудник видит источник и `verified: false`.

Для данных сервера допускается `provider` вместо `filename`: сервер отвечает
за их происхождение и подтверждения полноты.

## Результат для кабинета сотрудника

У `/jobs`, `/analyze` и callback финансовый объект лежит в
`result.financial_analysis`. У `/financial/prepare` он возвращается напрямую.

| Блок | Что отображать/использовать |
| --- | --- |
| `application` | ID, версия, ИНН, продукт, сумма, срок, ставка, расчётная дата |
| `annual_model_input` | Ровно 10 входов существующей модели, источники, год, единицы, `ready`, `missing_fields` |
| `cash_flow.months` | Реальные месячные итоги для графика, полнота покрытия, счета и источники |
| `cash_flow.average_*` | Средние поступления, списания и **остатки на конец месяца**, не среднедневной остаток |
| `cash_flow.latest_observed_balance_*` | Последний подтверждённый остаток и его дата, не текущий онлайн-остаток банка |
| `statistics` | Текущая/денежная ликвидность, маржи, капитал/активы, Долг/EBITDA, DSCR, стоимость залога, концентрация поступлений |
| `next_month_forecast` | Период, метод, базовый/осторожный/стрессовый сценарии, помесячный мост, доступный бэктест |
| `document_fields` | Таблица прочих извлечённых полей с источниками и их собственными единицами |
| `client_requests` | Что загрузить/уточнить, зачем, для каких расчётов, обязательность, действие |
| `employee_recommendations` | Проверка источников, подтверждение счетов, ввод платежа банка, дополнительные проверки |
| `warnings` | Противоречия, устаревшая история, отсутствие оценки сезонности, демонстрационные источники |
| `readiness` | Готовность каждого анализа отдельно; одного общего флага недостаточно |
| `model_outputs` | Вывод годовых ML-моделей: заполняет узел (`POST /v1/predict`); пока не выполнен — `not_run` и пусто. Django ML не запускает; см. [контракт инференса](ml-inference-contract.md) |

Нормализация годовых входов: **тысячи рублей**, `okved_group` — строка.
Выручка и прибыль — один полный календарный год, баланс — на конец этого же
года. Месячные движения, долги, оценка обеспечения и сценарии — **рубли**.
Маржи в `statistics` — доли (`0.05` = 5%), результаты моделей с суффиксом
`_percent` — проценты. Отрицательные прибыль и капитал допустимы.

Неизвестное не заменяется нулём, чистая прибыль не подставляется вместо
операционной, прибыль от продаж — вместо EBITDA, прибыль — вместо CFADS.
Отчётные денежные потоки за год не превращаются искусственно в месяцы.

Годовой инференс — отдельный опциональный шаг узла, а не автоматическое
действие Django:

```python
financial = node_result["result"]["financial_analysis"]
if financial is not None and financial["readiness"]["annual_model"]:
    model_input = financial["annual_model_input"]["metrics"]
    # Узел при готовых входах может сам (в своей реализации POST /v1/predict)
    # посчитать ML-прогнозы и вложить model_outputs в тот же callback до его
    # отправки. Django ML не запускает и такого endpoint не имеет — здесь
    # только чтение уже присланного результата узла.
```

Перед реальным использованием выводов модели также проверяйте `is_mock`,
предупреждения и версию документов, а `model_outputs.status` (`not_run` —
расчёт ещё не выполнялся). Готовность означает наличие согласованных входов, а
не одобрение кредита или подтверждение достоверности документов.

### Замечание клиенту

```json
{
  "code": "dscr_inputs_missing",
  "title": "Данные для DSCR",
  "message": "Для DSCR предоставьте денежный поток, доступный для обслуживания долга (CFADS), и полный график обслуживания долга за тот же период.",
  "fields": ["cfads", "debt_service"],
  "required_for": ["dscr"],
  "priority": "optional",
  "action": "upload_or_clarify",
  "filename": null
}
```

`required` блокирует указанный анализ/полноту текущей проверки; `optional`
означает дополнительный анализ: годовой скоринг при готовых 10 входах можно
выполнять, даже если EBITDA или оценка DSCR пока недоступны.
Кнопки загрузить/заменить/удалить и отправку запроса клиенту реализует Django.
Фраза «поле не извлечено» не должна превращаться в обвинение «его нет в оригинале».

## Месячная статистика и прогноз

Нужны минимум три последовательных **полных** месяца по всем подтверждённым
счетам и согласованные остатки. Остаток начала + все поступления − все
списания должен совпадать с остатком конца с допуском 2 копейки.
Отсутствующий счёт/месяц не заполняется нулями. Подтверждённый полный месяц
без операций может иметь нулевые движения.

База — среднее последних трёх месяцев отдельно для поступлений покупателей
и операционных списаний. Переводы между своими счетами и полученные займы
не входят в поступления покупателей. Суммарные `inflows/outflows` включают
все движения, в том числе переводы, и не являются выручкой/операционными
расходами. При отображении оборотов учитывайте эту разницу.

По умолчанию целевой период — следующий календарный месяц. Если сегодня
24 октября и последняя полная выписка — сентябрь, строится сценарный мост
на октябрь и ноябрь от сентябрьского остатка. Мост отражён в `projection_path`;
октябрь не выдаётся за уже наблюдённый факт. Для остатков нужны графики долга
за **весь мост**, а не только целевой месяц. Нода поддерживает горизонт до
двух месяцев после последнего наблюдения и требует свежую закрытую выписку.

Заданные сценарии: базовый `1.0/1.0`, осторожный `0.9/1.1`, стрессовый
`0.8/1.2` для поступлений/операционных расходов. Это фиксированные допущения,
не обученная ML-модель, вероятности или доверительные интервалы.
Платёж нового кредита применяется в целевом месяце; его поступление и прочие
неучтённые будущие потоки не моделируются. Сценарный остаток не является
полным бюджетом движения денежных средств.

`cash_gap_rub` — дефицит **на конец целевого месяца** при этих допущениях.
Он не исключает внутримесячного разрыва. `cash_gap_probability` и
`confidence_interval` остаются `null`. Бэктест — исторический rolling-origin
на том же горизонте, без подглядывания в будущее; при недостатке истории
MAE/MAPE также `null`. Годовая сезонность этим базовым методом не оценивается.

DSCR считается как `CFADS / обслуживание долга` за один подтверждённый период.
Долг/EBITDA требует совокупного долга и EBITDA согласованного периода.
Нулевой/отрицательный знаменатель не превращается в бесконечный коэффициент.

## CSV операций: детерминированный путь

UTF-8, разделитель запятая или `;`, обязательный заголовок:

```csv
transaction_id,account_id,date,direction,amount,currency,category,counterparty_id
1,account-1,2026-09-10,in,150000.00,RUB,customer_receipt,buyer-1
2,account-1,2026-09-11,out,40000.00,RUB,operating_payment,supplier-1
```

Дата ISO, сумма неотрицательная в рублях с точностью до копейки, направление
`in`/`out`. Категории входа: `customer_receipt`, `internal_transfer`,
`loan_received`, `other_inflow`. Категории выхода: `operating_payment`,
`debt_principal`, `debt_interest`, `debt_fee`, `internal_transfer`,
`capital_expenditure`, `other_outflow`. Налоги операционной деятельности
включаются в `operating_payment`; обслуживание долга учитывается отдельно.

Категории должны поступать из проверенной классификации, а не угадываться
по положительной/отрицательной сумме. `counterparty_id` может быть пустым,
но тогда концентрация покупателей недоступна. Максимум 100000 операций.
Идентичные `transaction_id` одного счёта не удваиваются; конфликтующие
отклоняются. Повторные одинаковые месячные итоги одного счёта также не суммируются.

В `statement_periods` укажите точное имя файла, счёт, период и остатки. Иначе
движения будут извлечены, но полнота месяца и прогноз не подтверждаются.
Обычный произвольный CSV/Excel/PDF идёт через извлечение: модель берёт только
явно приведённые месячные итоги, а не суммирует длинную выписку мысленно.
При недостатке итогов нода предлагает машиночитаемую выписку в этом формате.

## Статусы, callback, версии

Внешний `status: completed` означает завершение обработки, не одобрение.
Внутри `result.status`:

- `complete`: обязательные данные текущей проверки собраны;
- `needs_documents`: есть обязательные запросы документов/сведений;
- `needs_review`: нечитаемость, неопределённость, конфликт или неизвестный продукт;
- `processing_error`: техническая ошибка модели/инфраструктуры; нет оснований
  автоматически требовать от клиента новые документы, `financial_analysis: null`.

У callback остаются прежние поля: `job_id`, `status`, `result`, `files`,
`verification_status`, `model`; авторизация — Bearer `CALLBACK_TOKEN`.
`verification_status` — `needs_review` либо `not_verified`.
`result.application_context` содержит исходный нормализованный контекст задачи.
Старые сохранённые результаты остаются в прежней версии; проверяйте
`schema_version`, а не переписывайте их новым форматом задним числом.

Feedback доставляется отдельно в Django `/api/v1/document-node/feedback/`,
постоянный `feedback_id` обеспечивает идемпотентность. Передаются до 50
замечаний в пределах 256 KiB; полный список остаётся в callback/результате.
Порядок callback и feedback не гарантируется. Повторяются сетевые ошибки,
404, 408, 429 и 5xx feedback. Подтверждения см. `/jobs/{job_id}/delivery`;
`no_receipt` не различает ожидание, отсутствие настройки и сбой доставки.

Одна заявка остаётся у того же сотрудника. После изменения документов Django
создаёт новую версию и новый POST `/jobs` с полным актуальным комплектом.
Старый callback сохраняется в истории и транзакционно не меняет состояние
новой версии. Технический повтор без изменения файлов — новая попытка с новым
job_id; повтор доставки уже готового job_id использует сохранённый результат.
POST `/jobs` сам по себе не идемпотентен: Django предотвращает дубли отправки.

## Что брать для интерфейсов на примерах

- Страница заявки: данные Django + `application`, `statistics`, `cash_flow`,
  `next_month_forecast`; состояние выводить из `readiness` по каждому блоку.
- Документы: `files`, `document_fields`, источники годовых метрик, `issues`,
  `client_requests`; версии и события загрузки/удаления хранит Django.
- Финмодель: входы ноды + результаты существующего ML-сервиса. У него есть
  прогноз выручки/маржей, вероятность убытка и дефицита ликвидности; они не
  являются вероятностями дефолта или одобрения. Прогноз операционного потока
  также не получается автоматически из 10 текущих годовых входов.
- Портфельная аналитика: агрегаты заявок, решений, сотрудников, сроков и версий
  из Django. Нода возвращает `processing.duration_ms`, число файлов/наблюдений,
  коды причин и сведения доставки. Точность извлечения в процентах требует
  размеченной контрольной выборки, её нельзя получить из самооценки LLM.

## Ограничения и ошибки HTTP

1–5 непустых файлов, каждый до 10 MiB. Форматы: PDF, JPG/JPEG, PNG, TIF/TIFF,
DOCX, XLSX, PPTX, TXT, CSV, JSON, MD; XLS не поддерживается. Имена уникальны,
до 255 символов. Передаваемый `system_prompt` — до 20000 символов.

PDF с полноценным текстовым слоем читается без OCR. Для OCR сканов и
многостраничных изображений — до 10 страниц/кадров. Извлечение обрабатывает
до 12 текстовых фрагментов по 12000 символов на пакет. Файл, который проверен
не полностью или имеет сомнения OCR, не используется для финансовых входов;
это явно отражается в замечаниях. Техническая ошибка генерации OCR отделена
от нечитаемого/повреждённого файла.

HTTP 400 — контекст/лимиты количества/имён; 401 — неверный ключ;
413 — размер; 415 — формат; 422 — пустой файл/невалидный JSON-body финансовой
подготовки; 503 — очередь/ключ не настроены. Неизвестный job_id — 404.
Сохранённый результат доступен даже после истечения срока хранения RQ job,
пока его не удалил cleanup. Гибель процесса, сбой диска/Redis и исчерпание
доставки требуют мониторинга; гарантии завершения при недоступной
инфраструктуре нет.

[финансовый результат](schemas/financial-result-v2.schema.json).
